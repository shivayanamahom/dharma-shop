# Быстрый разбор компонента импорта (Claude, 2026-10-13)

Только чтение: `com_dharmashop_import` и `plg_dharmashopimport_xlsx` в состоянии рабочего дерева около 16:00 (Codex правил `Workflow`, `Storage`, `Profile`). Замеры — на изолированных таблицах (`imqa_*`, удалены), каталог не затрагивался. Сильные стороны (фазы с журналом, аренда шага, блокировки, SSRF-защита с закреплением DNS, XMLReader без DTD и сущностей, закрытое хранилище) в списке не повторяются; `php -l` и паритет RU/EN языковых файлов в порядке.

## A. Узкие места (блокируют большие файлы)

1. **Квадратичная проверка дубля цели.** `Workflow::work()`, фаза `checking`: для каждой строки-обновления `SELECT id FROM import_rows WHERE job_id=? AND target_id=? AND key_hash IS NOT NULL AND id<>?`. Индекса `(job_id, target_id)` нет, MySQL идёт по `uq_line` и перебирает все строки запуска. Замер: **28,7 мс на строку при 50 тыс. строк = ~24 мин** только на этот запрос, при 100 тыс. строк ~1,6 ч. Регулярное обновление цен — это 100 % строк-обновлений. Лечение: индекс `(job_id,target_id)` или уникальный ключ и перехват дубля при записи.
2. **Одна «плохая» строка при применении роняет весь запуск.** В ветке `applying` исключения `STALE`, `CONFLICT`, `RECOVERY`, `BUSY` и ошибка модели (`throw new RuntimeException($model->getError())`) не ловятся построчно: запуск уходит в `failed`, «Продолжить» упирается в ту же строку, остальные строки не применяются, `skip_errors` не помогает. Лечение: строка получает `error` и обработка идёт дальше; `failed` — только для инфраструктурных сбоев.
3. **Мало работы за шаг и лишние запросы.** Чтение — 100 строк, проверка и применение — по 20 за шаг (цикл идёт до дедлайна 3 с, но выборка уже ограничена), скачивание — 1 файл за шаг. На каждом шаге несколько `COUNT(*)` по всем строкам запуска (замер: ~27 мс), выборка порции применения `state IN (...) ORDER BY id` даёт filesort (~35 мс). Для 100 тыс. строк это тысячи HTTP-шагов. Лечение: брать порцию по времени, а не по числу строк; счётчики — инкрементально; общий индекс под очередь.
4. **Дорогие запросы на каждую строку.** `Records::prepare()` создаёт `new Schema($db)->fields()` и `new Dependencies` на каждую строку (запрос определений полей), опции списков ищутся отдельным запросом на значение, полная карточка `item()` загружается 3+ раза (prepare, assertAccess, applyLocked, matches), `validate()` дважды (finalizing и apply), `keyHash()` — запрос `WEIGHT_STRING` на строку. Лечение: кэш схемы и опций на время шага, один `before` на строку.
5. **XLSX нормализуется внутри веб-запроса.** `Workflow::start()` и `ProfileModel::save()` вызывают `sample()`/`normalize()` синхронно; `sample()` для двух строк сначала распаковывает весь лист (до 128 МБ) во временный файл. Файл на 100 тыс. строк упрётся в `max_execution_time`. Лечение: читать лист потоком из ZIP (`zip://`) с остановкой после 2 строк, полную нормализацию вынести в шаги фазы `reading`.
6. **Нет очистки.** Каждая строка файла хранится в БД дважды (сырая и плановая `payload`, плановая с `before`), исходный и нормализованный файлы лежат на диске, URL-источник скачивается заново при каждом сохранении профиля и каждом старте. Автоочистки и удаления запусков нет (в `ADMIN_IMPORT.md` это честно указано). Минимум: удаление запуска с его строками и файлами, «Очистить историю», правило хранения.
7. **Лимиты медиа малы для первичной загрузки.** По умолчанию 5000 файлов и 512 МБ на запуск, файл не больше 16 МБ; 20 тыс. товаров с тремя фото упрутся в квоту, а в общем плане сказано «не блокировать». Нужна настройка на профиль и догрузка в несколько запусков.

## B. Логические несостыковки

8. **Бренд, бейджи и дополнительные категории — только по числовому ID** (`Schema`: `brand_id=>'id'`, `badge_ids=>'ids'`, `extra_catids=>'ids'`). Прайс поставщика содержит названия («Pixel»), ID чужого магазина бесполезны. Категория по пути есть, бренд по названию — нет. Нужны поиск по алиасу/названию (как у категорий) и опция автосоздания.
9. **Хвост `-<12 hex>` в алиасе каждой созданной записи** (`Records::prepare`: `stringURLSafe(title).'-'.substr(sha256(source|key),0,12)`). Алиас — часть адреса на витрине, все импортированные товары и категории получают некрасивые URL. Лучше обычный слаг и суффикс только при конфликте в своей категории/родителе.
10. **`state` принимает только `0`/`1`**, а флажки полей — `1/true/да/yes`. Столбец «Опубликован: Да/Нет» из прайса вернёт ошибку значения; булевы из XLSX приходят как `TRUE/FALSE`.
11. **Заголовок — всегда первая строка.** Нет «строка заголовков №» и «пропустить N строк»; в XLSX поставщиков над таблицей обычно шапка с названием и датой.
12. **Пустые «хвостовые» строки дают ошибки.** `readRow()` XLSX возвращает массив пустых строк для ячеек только со стилем (таких строк в конце листа часто тысячи), а CSV-проверка пропускает только `['']`. Каждая такая строка — ошибка `KEY_ERROR`, а ошибки блокируют применение. Строки, где все ячейки пусты, нужно отбрасывать.
13. **Ключ `alias` у категорий неоднозначен**: `find()` ищет алиас по всему типу, а в Joomla он уникален только внутри родителя; законные одноимённые алиасы дают `CONFLICT`.
14. **Круговая проверка «экспорт → импорт» не восстанавливает остаток**: `Schema::automatic()` нарочно не сопоставляет экспортную колонку `stock` (в экспорте нет колонки `stock_qty`). Для цели E5 нужна совместимая колонка или явная подсказка в сопоставлении. Апостроф защиты формул при импорте тоже не снимается (план обещал режим «файл Dharma Export»).

## C. XLSX (`Reader.php`)

15. **Формулы и ошибки отклоняют весь файл** (`<f>` и `t="e"` → `XLSX_FORMULA`). Прайсы с `=B2*1.2` и строкой итогов — обычное дело. Безопаснее читать кэшированное значение `<v>` (формула не выполняется), а ошибочную ячейку считать пустой или ошибкой строки.
16. **Rich-text в `inlineStr` теряет начало**: `$value=$r->readString()` перезаписывается каждым `<t>`; остаётся последний фрагмент. Нужно склеивать.
17. **Даты приходят числами** (серийные номера Excel), стили не читаются; `discount_start/end` дадут ошибку. Нужен разбор `styles.xml` или явный формат даты в профиле.
18. **Потолки общих строк** 250 000 штук и 32 МБ: 100 тыс. товаров с уникальными описаниями их превышают, файл отклоняется как «лимит». Либо поднять и хранить индекс на диске, либо явно сказать об этом в справке.
19. **Сообщения плагина не доходят до пользователя**: `Workflow::message()` пропускает только ключи `COM_*`/`J*`, исключения `PLG_DHARMASHOPIMPORT_XLSX_*` превращаются в общий `COM_DHARMASHOP_IMPORT_FAILURE`. Плюс не определён `COM_DHARMASHOP_IMPORT_READER_MISSING`.

## D. Отчёт проверки

20. **Нет сводки до подтверждения**: на странице запуска только «обработано/всего · ошибок». Сколько создастся, обновится, не изменится, пропустится — нужно листать строки (счётчики `created_count` и т. д. заполняются только после применения). Нет фильтра «только ошибки», нет выгрузки ошибок в CSV, пагинация только вперёд по 100 строк. Для 100 тыс. строк найти ошибку практически нельзя.

## E. Мелочи

- `strip_tags` для текстовых значений вырезает обычный текст вида `Размер <S>`; для названий лучше экранирование.
- `ComponentHelper::filterText()` без пользователя (планировщик/CLI) применит гостевой фильтр.
- `CsvReader::row()` проверяет размер строки после чтения: незакрытая кавычка читает в память весь файл до отказа.
- `iconv('Windows-1251',…)` при недопустимых байтах возвращает `false`; сообщение об ошибке кодировки теряется.
- Источник по URL: список разрешённых хостов строится из самого URL, перенаправление на другой хост (например `www` → без `www`) запрещено без настройки.
