# Покупатели и оформление заказа (C73–C75)

## Просмотр покупателем и подтверждение (C75, 2026-10-08)

Подтверждение — компактная карточка Bootstrap: галочка, номер, дата, статус, сумма, «Перейти к заказу» и «Продолжить покупки». Читается сохранённый заказ; текущая корзина/каталог не подмешиваются. Срок самого подтверждения C74 остаётся 30 минут.

Отдельный вид `order&id=<id>` и тип меню «Заказ»: номер/дата/статус, состав с артикулом/вариантом/количеством/единицей/ценой/суммой, заполненные контакты из снимка, корректировки и итог. Замена нулевой цены учитывается, включая смешанную сумму с ценой по запросу. При изменении валюты магазина прежний заказ сохраняет свой код валюты. Доставка/оплата показываются только при наличии сохранённого названия; подключение способов остаётся следующим шагом.

Доступ проверяется в SQL до загрузки данных: аккаунт — только свой user_id; гость — ID из серверной сессии после успешного checkout, заказ обязательно без user_id. Последние 50 гостевых ID доступны до конца сессии. Существующий receipt C73 позволяет открыть уже созданный заказ в пределах его 30 минут без повторной отправки. Числовой ID, номер и совпадение контактов не авторизуют. Чужой/отсутствующий заказ — одинаковый 404. Secret, внутренние заметки и история сотрудников не выдаются. Кеш отключён, Cache-Control private/no-store, robots noindex/nofollow. Гостевой просмотр по постоянной ссылке вне сессии пока не реализован.

Макеты: `site/tmpl/order/default.php`, `default_items.php`, `default_contacts.php`, `default_summary.php`; стандартные переопределения шаблона Joomla. Пункт меню необязателен для кнопки, нужен для собственного адреса и модулей. Схема/версия не менялись. Адресная установка на test.test; синтаксис PHP/XML проверен. Браузерные сценарии, тестовые заказы и изменение существующих заказов не запускались.

## Уведомления и смена статуса (C76)

В карточке заказа добавлена нативная форма смены статуса: POST/CSRF и orders.manage, блокировка заказа и проверка прежнего статуса, активного нейтрального назначения и заданных переходов. Прежний статус не создаёт запись/письмо. Движение остатков не подключено; такие переходы отклоняются. После commit история передаётся каналам уведомлений. Текст для покупателя редактируется в статусе (customer_message, до 2000 символов).

В истории показываются результаты доставки по событию и кнопка повторить ошибки. SMTP не входит в транзакцию заказа. Для штатной отправки работает email-плагин; переключатели/получатели в настройках магазина, тексты в «Шаблонах писем». Полный контракт и ограничения — NOTIFICATIONS.md. После установки отправка выключена, существующие заказы не рассылались и не изменялись.

## Исправление связей покупателей (C78)

На test.test три гостевых заказа из одной корзины ошибочно использовали одного покупателя. Теперь сопоставление — по полной паре нормализованных email/телефон, с уникальным ключом в БД. Непустое имя карточки сохраняется, получатель берётся из снимка заказа. Заказы 000001/000002 привязаны к восстановленным карточкам №2/№3, заказ 000003 сохранил №1. Снимки, состав, суммы, история и журнал уведомлений сверены без изменений; повторной рассылки нет. Подробнее CUSTOMER_IDENTITY.md.

## Предыдущие шаги

2026-10-08. Пользователь согласовал порядок: покупатели → гостевой заказ → заказы/отправка чекаута. Всё в com_dharmashop, отдельные службы Customer/Order; доставка, оплата, уведомления будут расширениями.

## Границы первого шага

- Покупатели: нативный список, поиск, карточка контактов/заметки, связь с Joomla только по user_id, история заказов. Контакты заказа — самостоятельный снимок и не меняются при правке покупателя.
- checkout_guest: Да по умолчанию. Нет требует входа и на странице, и в обработчике POST. Гостевой заказ не создаёт аккаунт Joomla. Введённый email не доказывает владение аккаунтом/записью покупателя.
- Заказы: список и просмотр снимка, контактов, согласий, позиций, итогов и истории. Начальный статус «Новый» с stock_effect=0, без резервирования/списания. Смена статуса заказа/движения остатков, доставка/оплата/письма — последующие шаги.
- Создание: POST+CSRF, серверные проверки контактов/согласий/прав гостя, повторное чтение корзины/цен и ошибок. Запись покупателя, заказа, позиций, итогов, начальной истории и очистка корзины в одной транзакции, без Table::store и неявных LOCK TABLES.
- Повторная отправка: случайный ключ формы связан с серверной сессией, корзиной и user_id, уникальный orders.secret + блокировка корзины. Повтор того же запроса возвращает номер созданного заказа. Номер первого шага — ID с ведущими нулями, шесть разрядов минимум.
- Снимок в существующем orders.contacts: version, fields (name/label/type/value), consents (имя, точный текст/URL/подпись, обязательность, accepted, время). Без схемных изменений.
- Основные контакты: первые включённые email/tel; имя из текстового поля с техническим именем name/recipient_name/full_name/fio/imya либо подписью Имя/ФИО/Фамилия имя отчество/Full name/Name. Остальные поля всегда остаются в снимке. Произвольный первый текст не считается именем.
- Покупатель при заказе (уточнение C78): вошедший — запись по user_id; гость с полной парой email/телефон — одна карточка по contact_key, независимо от корзины и имени получателя. Разные/неполные пары — отдельные карточки. Непустое имя карточки не заменяется, имя заказа сохраняется в снимке. С аккаунтом по контактам не объединяем. CUSTOMER_IDENTITY.md.
- Успешная страница показывает только номер из серверной сессии. Публичного просмотра чужих заказов по ID/секрету нет. Ошибки возвращают введённые поля, согласия снова сняты.

## Справочник статусов

По дополнительному запросу пользователя — отдельный пункт «Статусы заказов». Нативные список/поиск и редактор Form XML: название, алиас, цвет, порядок, состояние, начальный статус. «Новый» создаётся только в пустом справочнике при установке или первом обращении службы. Начальный статус должен быть опубликованным и нейтральным; сначала выбирают другой начальный, затем отключают прежний. Назначение начального снимает флаг с остальных одним атомарным UPDATE. Новые статусы пока без эффектов остатков/писем. Редактор: dharmashop.orders.status + core.create/edit; публикация/порядок/начальный: core.edit.state. Заказы: orders.manage, покупатели: customers.view. Удаление заказов/покупателей/статусов не предоставляется.

## Стадия

C74: результат вынесен в отдельный вид checkoutcomplete, тип пункта меню «Заказ оформлен». После POST маршрут выбирает назначенный пункт штатными MenuRules; без него остаётся обычный компонентный адрес. Старый checkout?completed=1 перенаправляется в новый вид. Своя сессия/user_id и срок 30 минут сохранены; без подтверждения нейтральное сообщение. Адрес и назначение модулей задаются обычным пунктом меню Joomla. Корзина/данные заказа в новом виде не читаются из БД.

Реализовано и адресно установлено на test.test: три пункта меню (515/516/517), начальный нейтральный статус (ID 1), формы/макеты/службы/контроллер, гостевой доступ и RU/EN. Настройки пользователя не пересохранялись; checkout_guest использует default=1. Новые таблицы не потребовались. Синтаксис PHP/XML/JS проверен. Автоматические тесты, сохранение покупателя/статуса и пробная отправка заказа не запускались. Следующий шаг при запросе пользователя — первый заказ через реальную форму.

## Остатки: списание и возврат (2026-10-08)

- **Списание.** При создании заказа (в той же транзакции) остаток списывается по вариантам с включённым учётом остатков (у товара, категории или в настройках): `StockService::consume` — один `UPDATE` с условием «доступно ≥ количества» (поэтому два одновременных заказа не уведут остаток в минус), запись в журнал движений (`reason = order`, `order_id`), пересчёт `stock_total` и `in_stock` (на нуле у карточки и страницы товара пропадает кнопка «В корзину», сервер тоже не даёт добавить). С включённым «продавать без остатка» остаток может уйти в минус. Товары без учёта остатков не затрагиваются.
- **Возврат.** У статуса заказа появился параметр «Остатки»: «списаны (обычный)» или «возвращает остатки (отмена)». Переход в статус с возвратом возвращает списанное под заказ (`order_return`); обратный переход списывает снова, если на складе хватает. Работает по журналу движений: повторное применение ничего не меняет, а заказы, оформленные до появления списания, остатков не трогают. Ограничение: резерва до оплаты нет (списание при оформлении), несколько складов пока не используются.
- **Статус по умолчанию** (начальный) всегда «обычный».

## Привязка гостевых заказов к аккаунту (2026-10-08)

Настройка «Привязывать гостевые заказы к аккаунту» (вкладка «Оформление заказа»): «Только при подтверждённой почте» (по умолчанию), «Не привязывать», «По любому совпадению e-mail» (небезопасно). При открытии «Моих заказов» (один раз за сессию) заказы с `user_id IS NULL` и тем же `contact_email` получают `user_id` пользователя. «Подтверждённая почта» = в настройках пользователей Joomla включена активация по ссылке из письма (`useractivation = 1`) и пользователь её прошёл; при «Активации: нет» привязки не происходит. Записи покупателей (`customers`) не объединяются.

## Срок жизни корзины (2026-10-08)

Настройки «Корзина»: срок корзины гостя (по умолчанию 30 дней, он же срок cookie) и срок корзины вошедшего пользователя (по умолчанию 365 дней, `0` — без срока). Срок скользящий: продлевается при каждом изменении корзины. Корзина пользователя лежит в базе и доступна с любого устройства.

## Раздел «Корзины» в админке (2026-10-08)

Меню «Dharma Shop → Корзины» (`view=carts`, нативный список с поиском и фильтрами; право `dharmashop.orders.manage`): корзины гостей и пользователей — владелец (ссылка на пользователя Joomla), состав (первые позиции, число позиций и штук), сумма по **текущим** ценам (корзина цен не хранит), дата изменения, срок (бейдж «Просрочена» или «Без срока»), секретный ключ (токен корзины) и ссылка «Открыть на сайте (только чтение)». Фильтры: владелец (все/пользователи/гости), срок (действующие/просроченные), состав (с товарами/пустые), поиск по номеру, имени, логину, e-mail и началу ключа; сортировки по изменению, сроку, созданию. Действия: «Удалить» выбранные (с позициями; заказы не затрагиваются) и «Очистить просроченные» (`CartService::purgeExpired`); обе — POST с токеном и правами `core.delete` + `dharmashop.orders.manage`. Пустые корзины не хранятся: при оформлении заказа, «Очистить корзину» и удалении последней позиции строка корзины удаляется (`CartService::dropIfEmpty`), новая создаётся при добавлении товара; `orders.cart_id` остаётся справочным. «Очистить просроченные» убирает также пустые корзины старше суток (остались от прежних версий).

**Просмотр корзины на сайте:** `/korzina?cart=<токен>` показывает корзину по ключу, только если посетитель вошёл с правом `dharmashop.orders.manage`; страница только для чтения (`fieldset disabled`, скрипт корзины не подключается), не индексируется, `Referrer-Policy: no-referrer`; без права параметр игнорируется (показывается собственная корзина посетителя). Просроченную корзину по ключу не открыть.

Пункт меню добавляется манифестом (`<submenu>`); на уже установленном сайте — обновлением пакета; для тестового стенда — `php dev/add-admin-menu.php`.

## Ссылка гостю на заказ и секрет в админке (2026-10-08)

Письмо покупателю (если включена ссылка) содержит для гостевого заказа адрес `…?option=com_dharmashop&view=order&id=N&key=<секрет>`: заказ открывается без сессии и срока (`OrderModel`: `orders.secret` совпал и `user_id IS NULL`; вошедшему пользователю — тоже, если заказ оформлен им гостем); заказ вошедшего пользователя открывается только после входа. Страница отдаёт `Referrer-Policy: no-referrer`. В админке в заказе показан секретный ключ и (для гостевого заказа) кнопка «Открыть заказ на сайте (как покупатель)»; у заказа и покупателя с аккаунтом — ссылка на пользователя Joomla.

## Стандартные статусы (2026-10-08)

При первой установке пакета, если в справочнике нет ничего, кроме начального «Новый», добавляются: В обработке, Ожидает оплаты, Оплачен, Отправлен, Доставлен, Выполнен (конечный), Отменён (возвращает остатки, конечный), Возврат (конечный). Названия и тексты покупателю берутся из языкового файла на языке установки и дальше правятся в «Статусах заказов»; уже настроенный справочник не трогается (`Order\DefaultStatuses`).
