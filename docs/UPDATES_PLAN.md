## 1. Цель и главный принцип

Два пути обновления, **один механизм**:

1. **Штатный Joomla:** Система → Обновления (Update → «Найти обновления» → «Обновить»), команда `php cli/joomla.php update:extensions:check`, уведомления Joomla об обновлениях расширений.
2. **Наша кнопка** «Обновить» в Dharma Shop → Настройки → Расширения (рядом с каждым расширением и «Обновить всё»).

Кнопка не устанавливает ничего своим кодом: она вызывает тот же `Joomla\Component\Installer\Administrator\Model\UpdateModel` (поиск и `update($uids)`), что и штатный экран. Поэтому результат, проверка контрольных сумм, права и журнал одинаковы, а состояние («есть обновление») хранится в одном месте — таблице `#__updates`. Никакой отдельной «копилки версий» у нас не будет.

## 2. Что есть сейчас

- Один пакет `pkg_dharmashop` (38 частей внутри: 4 компонента, библиотека макетов, 27 плагинов (в том числе необязательный плагин Radical Sitemap), 6 модулей). Релиз — pre-release на GitHub с zip и `.sha256`.
- Версия во всех манифестах `0.1.0`: у dev-сборок меняется только имя zip. Для Joomla это «та же версия», поэтому штатное обновление не сработало бы.
- В манифестах **нет `<updateservers>`**, у Joomla нет адреса, где искать обновления.
- Репозиторий **закрытый**: Joomla (и любой сайт клиента) не может скачать релиз с GitHub без токена.
- Схема БД меняется «по месту»: `CREATE TABLE IF NOT EXISTS` в install-SQL и ручные `ALTER` на стендах; `sql/updates` нет, поэтому штатный механизм миграций Joomla не используется.
- Уже есть вкладка «Расширения» в настройках, но только для библиотек Swiper и Fancybox (C64: версии с GitHub Releases, «Обновить», «Откатить», проверка по кнопке).

## 3. Как Joomla обновляет расширения (то, на что опираемся)

- В манифесте расширения `<updateservers><server type="extension|collection" name="…" priority="1">URL</server></updateservers>`; при установке адрес попадает в `#__update_sites`.
- По адресу лежит XML: `<updates><update>` с `name`, `element`, `type`, `folder`, `client`, `version`, `<tags><tag>stable|rc|beta|alpha|dev</tag>`, `<downloads><downloadurl type="full" format="zip">…</downloadurl>`, `<sha256>` (поддерживаются sha256/sha384/sha512, Joomla сверяет скачанный файл), `<targetplatform name="joomla" version="6.*"/>`, `<php_minimum>`, `<infourl>`, `<changelogurl>`.
- Тип `collection` — список ссылок на XML отдельных расширений: один адрес в манифесте, а обновляются все расширения из списка по отдельности.
- «Минимальная стабильность» (Установка → Параметры) решает, какие метки (`dev`, `alpha`…) Joomla показывает. Номера сравниваются как `version_compare`: `0.1.0-dev.5` > `0.1.0-dev.4`, а `0.1.0` > любой dev.
- Платные/закрытые источники: Joomla дописывает к адресам ключ загрузки (`extra_query`, поле «Ключ загрузки» у сайта обновлений), если он задан.
- Если у расширений внутри пакета есть свои `<updateservers>`, у каждого появляется собственный сайт обновлений — их можно обновлять отдельно, не трогая пакет.

## 4. Архитектура

```
  GitHub (закрытый репо)            Публичная точка раздачи
  ───────────────────────           ─────────────────────────────────────────
  tag vX → dev/release.sh  ───►     updates/collection.xml   (список расширений)
  (сборка, версии, хэши)            updates/<element>.xml    (версия, sha256, URL zip)
                                    releases/<tag>/…zip      (пакет + отдельные zip)
                                                  │
                  ┌───────────────────────────────┴──────────────────────┐
                  ▼                                                       ▼
       Joomla: Система → Обновления                  Dharma Shop → Настройки → Расширения
       update:extensions:check, уведомления          таблица + кнопки «Проверить / Обновить / Обновить всё»
                  └──────────── один механизм: #__update_sites / #__updates / UpdateModel ───┘
```

### 4.1. Раздача (решение нужно)

Закрытый репозиторий не может быть источником обновлений. Варианты:

| Вариант | Что это | Плюсы | Минусы |
|---|---|---|---|
| **A. Публичный репозиторий релизов** `dharma-shop-updates` (рекомендую для старта) | Исходники остаются в закрытом репо, в публичный репо `release.sh` кладёт zip в Releases и XML-ленту в ветку `gh-pages` (GitHub Pages) | бесплатно, без своего сервера, быстрый CDN; код всё равно GPL | пакеты доступны всем, у кого есть ссылка |
| B. Свой домен/хостинг | Статический каталог на своём сервере | любые адреса и логика | нужен сервер и сертификат |
| C. Закрытая раздача по ключу | Небольшая прослойка (функция на Cloudflare Workers / PHP-скрипт) проверяет `dlid` и отдаёт zip из закрытого репо по токену | лицензирование, платные обновления | сложнее, нужен ключ у клиента |

План: стартуем с **A**; формат ленты и ключ загрузки закладываем сразу, чтобы перейти на C без смены клиентов (адрес меняется один раз, через обновление).

### 4.2. Версии

- У пакета и **у каждого расширения своя версия** (формат `0.1.0-dev.5`, затем `0.1.0-rc.1`, `0.1.0`). В репозитории манифесты хранят реальную версию, а не `0.1.0`.
- `dev/release.sh` сам определяет, что менялось с прошлой метки (`git diff --name-only vПРОШЛАЯ..HEAD -- <папка расширения>`), увеличивает версию только у изменённых расширений и всегда у пакета. Это даёт «плагин обновился, остальное нет».
- Согласованность: у каждого расширения в ленте есть необязательное поле `requires` (минимальная версия ядра `com_dharmashop`). Наша вкладка берёт его и обновляет ядро раньше плагинов; штатный экран Joomla про `requires` не знает, поэтому дублируем проверку в установщике (`script.php` расширения: preflight читает версию ядра из `#__extensions` и отказывает с понятным сообщением).
- Каналы: `dev` (сейчас), `rc`, `stable`. Канал = «Минимальная стабильность» Joomla; наша вкладка показывает и меняет **ту же** настройку, чтобы два экрана не расходились.

### 4.3. Лента обновлений

> **Уточнено 2026-10-14 по результатам проверки:** отдельный источник на каждое расширение (39 запросов на каждую проверку) оказался слишком медленным и ненадёжным. Применён вариант с **одним источником-коллекцией** `updates/dharma-shop.xml` (одна запись на расширение: версия и `detailsurl` подробной ленты); все манифесты указывают на этот адрес, Joomla создаёт один источник. Подробные ленты `updates/<расширение>.xml` читаются только при установке выбранного обновления. Описание ниже про `<updateservers>` на отдельные ленты относится к исходному замыслу.

- Манифест пакета `pkg_dharmashop.xml`: один `<updateservers>` типа `collection` на `…/updates/collection.xml`; в нём — запись на пакет и записи на каждое расширение.
- Манифест каждого расширения: свой `<updateservers>` на `…/updates/<тип>_<имя>.xml` (так отдельное обновление работает даже без пакета).
- Ленты генерирует `release.sh` из манифестов: версия, имя, `folder`/`client`, хэш `sha256` (считается по собранному zip), URL, `targetplatform` (Joomla 6.*), `php_minimum` (8.3), `infourl` и `changelogurl` (`CHANGELOG.md` в релизе). Вручную XML никто не правит.
- В ленте остаётся несколько последних версий каждого расширения (для «Откатить»), Joomla сама выберет самую новую подходящую.

### 4.4. Миграции БД

- Подключаем штатные: в манифестах компонентов `<update><schemas><schemapath type="mysql">sql/updates/mysql</schemapath></schemas></update>` и файлы `sql/updates/mysql/<версия>.sql` с идемпотентными операторами (`CREATE TABLE IF NOT EXISTS`, проверка колонки перед `ALTER`). Joomla ведёт версию схемы в `#__schemas`, раздел «Система → Информация → База данных» показывает расхождения.
- Правило для разработки: любое изменение схемы = файл миграции той же версии, где оно появилось. Кроме обновлений SQL, `script.php` (`update`) выполняет то, чего SQL не может (пересборка индексов, права по умолчанию), и всегда повторяем: обновление можно запустить дважды.
- Первая миграция фиксирует то, что уже поставлено вручную: индекс `idx_target` и таблицу `#__dharmashop_import_media` (сейчас создаётся налету при первом использовании).

### 4.5. Наша вкладка «Расширения»

- Таблица: расширение, группа (плагин: доставка, оплата, импорт…), установлено, доступно, состояние (включено/выключено, необязательное), канал; библиотеки Swiper/Fancybox (C64) входят в ту же таблицу отдельным блоком «Сторонние библиотеки».
- Кнопки: «Проверить сейчас» (`UpdateModel::findUpdates` по сайтам обновлений Dharma Shop, как «Найти обновления», только быстрее: один запрос на ленту), «Обновить» у строки, «Обновить всё», «Откатить до X» (установка предыдущей версии из ленты с той же сверкой хэша). Права: `core.admin` (как у `com_installer`), токен на каждой задаче.
- Порядок «Обновить всё»: ядро → компоненты → плагины → модули; после каждого шага проверка; остановка на первой ошибке с понятным сообщением, остальное остаётся как было.
- Предупреждения: нет прав на запись в файлы, FTP-слой, режим обслуживания (рекомендуем включать на время обновления ядра), напоминание о резервной копии базы; в окне после обновления — результат каждого шага и ссылка на журнал изменений.
- Без вкладки всё работает: если админ пользуется штатным экраном Joomla, наша таблица просто показывает уже новое состояние.

### 4.6. Уведомления и автоматика

- Штатное: задача планировщика Joomla «Update Notification» (`plg_task_updatenotification`, письмо суперпользователям) и иконка быстрого доступа «Обновления расширений» (`plg_quickicon_extensionupdate`) подхватывают наши расширения без доработок, как только появятся сайты обновлений.
- Своя мелочь: бейдж «Доступны обновления (N)» в меню Dharma Shop и на вкладке «Расширения».
- Автообновление не включаем по умолчанию; позже — задача планировщика «Обновлять патч-версии» (только для расширений, у которых меняется последний разряд версии, с письмом о результате).

### 4.7. Безопасность

- Только HTTPS-адреса; ссылка на скачивание берётся из ленты, но **имя хоста проверяется по списку** (домен раздачи); `sha256` обязателен для каждой записи.
- Лента подписывается (подпись `.sig` рядом, проверка нашей вкладкой; штатный экран Joomla подпись не проверяет — там защита хэшем и HTTPS). Подпись — второй этап.
- Откат и обновление идут через Joomla `Installer`, поэтому действуют его проверки структуры архива.

## 6. Риски и как их закрываем

- **Закрытый репозиторий** — решаем разделением «исходники» и «раздача» (вариант A/C), а не открытием исходников.
- **Версии, которые не меняются** (как сейчас) — `release.sh` проверяет, что версия изменившегося расширения выросла, иначе сборка не проходит.
- **Обновление частей ломает связку** (плагин новее ядра) — `requires` в ленте и preflight в `script.php`; порядок «Обновить всё».
- **Схема БД на старых стендах** — первая миграция идемпотентна; на сайтах, где часть уже создана, ничего не ломает.
- **Права и файловая система** — предупреждаем заранее, проверяем запись в каталоги до начала обновления.
- **Расхождение «пакет» и «части»** — пакет в нашей таблице отдельная строка-итог: актуален, если версии всех его частей не ниже включённых в пакет; при обновлении пакета целиком версии частей выравниваются.
- **Обновление через частично загруженный архив** — Joomla сверяет `sha256`; при несовпадении установка не начинается.
