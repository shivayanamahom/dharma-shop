# Фильтр товаров: архитектура и реализация (C84)

**Актуальная реализация F4–F8 на 2026-10-12 — [FILTER_IMPLEMENTATION.md](FILTER_IMPLEMENTATION.md).** Старые разделы плана и F0 ниже сохранены как история; замеры F0 не описывают скорость финального PHP-кода.

Дата: 2026-10-09. Статус: **планирование; F0 (замеры) выполнен 2026-10-09**, кода фильтра нет. Запрос пользователя: фильтр должен быть мощным и быстрым, модуль с большим числом настроек; нужен файл архитектуры; за образец настроек — свой прежний пакет `shivayanamahom/dharma-universal-filter`; нужные скрипты подключаются только если их требуют настройки. Решения — в «Что решаем» (§12); этап закрывает только пользователь.

## 1. Цели и границы

**Цели**
1. Фильтр по полям товара, цене, бренду, бейджам, наличию, акции и подкатегориям на страницах каталога, категории, бренда, бейджа и результатов поиска — одним механизмом, вместе с поиском `filter[search]`, сортировкой и пагинацией.
2. Скорость: размер каталога не имеет значения (100 и 100 000+ товаров), цель — список с фильтром ≤ 80 мс (замеры этапа 0: 6–32 мс на 100 тыс.), счётчики и каскад — в пределах бюджета §9, а не «50–100 мс на поле».
3. Работает **без JavaScript** (обычная GET-форма, ссылки, адреса для поисковиков); AJAX, ползунок, offcanvas и т. п. — надстройки, которые подключаются только настройками.
4. Мощные настройки: на уровне магазина (движок и SEO), поля (представление по умолчанию) и модуля (внешний вид, поведение, набор полей и их порядок).
5. Расширяемость: типы полей-плагинов сами умеют условие и значения фильтра (`dharmashopfield`); макеты переопределяются в шаблоне.

**Не цели первой версии:** фильтр по значениям текстовых полей (text/editor заблокированы, C62), по файлам/галерее; мультивалютные цены (точка расширения оставлена); «строгий вариант» (цвет и размер в одном варианте) — есть `variant_id`, но в v1 товар подходит, если подходит **любой** его вариант (как в ARCHITECTURE §5.5); сохранённые фильтры пользователя; ЧПУ вида `/katalog/cvet-krasnyj/` (позже, поверх тех же параметров).

## 2. Что берём из прежнего пакета (dharma-universal-filter) и что нет

Изучены: модуль, раскладки, индексатор, схема, скриншоты (README, `docs/architecture.md`). Он привязан к чужим моделям данных; берём идеи и набор настроек, код не переносим.

**Берём (с переработкой)**

| Прежняя настройка / возможность | В нашем фильтре |
|---|---|
| Категория: текущая / корень / выбранная | `category_mode` (`current` / `root` / `fixed`) + `category` |
| Пункт меню для отправки | `target_menu_item` (по умолчанию — страница каталога/категории, как у модуля поиска) |
| Раскладки `vertical` / `horizontal` | то же; общий набор макетов полей, переопределяемый в шаблоне |
| AJAX (вкл) + «мгновенно / по кнопке» | `ajax` + `apply_mode` (`instant` / `button`) |
| Кнопки «Применить» и «Сбросить» | `show_apply_button`, `show_reset_button` (+ число найденных на кнопке, «Показать 124») |
| Offcanvas: никогда / на мобильных / всегда | `offcanvas_mode` + порог `offcanvas_breakpoint` (sm…xl) |
| Липкий фильтр + отступ сверху | `sticky` + `sticky_offset` (отступ — задаёт скрипт; своих стилей нет) |
| «Отсутствующие значения»: показать / скрыть / отключить | `empty_options` (то же) |
| Каскад (доступность по текущему выбору) | `cascade` |
| Цена: поля / ползунок | `price_display` (`none` / `inputs` / `slider` / `both`) + шаг |
| Чекбоксы: все / ограничить N | `checkbox_limit` + «Показать ещё» (+ поиск внутри длинного списка) |
| Счётчики у значений | `counts` (`off` / `base` / `live`) — см. §6 |
| Чекбоксы-дропдаун (бейдж с числом выбранных, «×») в горизонтальном макете | макет `dropdown` для поля (Bootstrap Dropdown, подключается по необходимости) |
| Конфигурация полей: поле, показывать, заголовок, шаблон, «открыто», порядок | `fields_config` (подформа): поле или системный фильтр, показывать, заголовок, представление, раскрыто, **логика ИЛИ/И**, сортировка значений, лимит, счётчики поля |
| Системные «поля»: категории, производители, бейджи, наличие | системные фильтры: подкатегории, бренд, бейджи, наличие, **акция** |
| Модуль без кэша | не кэшируется модулем (вывод зависит от адреса); кэшируются данные внутри §6.4 |
| Индексатор: пакетами, транзакция, сброс кэша | `FacetIndexer` (§5.4): те же принципы, на нашем индексе витрины |

**Не берём**

| Прежний приём | Причина |
|---|---|
| Свой индекс «категория × поле × значение» (дублирует `field_values` для каждой категории) | у нас уже есть `field_values` с нужными индексами и `product_categories` с родительскими строками |
| Множества `item_id` тянутся в PHP, пересекаются `array_intersect`, потом `IN (…)` списком | ломается на больших каталогах (память, длина запроса, время); у нас условия — SQL-подзапросы, множества не покидают базу |
| Пересчёт доступности по всем значениям на каждый запрос | кэш + предрасчёт базового состояния (§6) |
| Привязка к чужим моделям (модели, поля, валюта) | наша схема и сервисы |
| Скрипты подключаются при `ajax=1` одним файлом | подключение по набору включённых возможностей (§8) |
| `ANY_VALUE`, `COUNT(DISTINCT)` по большим таблицам | запросы по покрывающим индексам, уникальность гарантирована схемой/EXISTS |

## 3. Что уже есть в проекте (опираемся на это)

- **Значения полей** `#__dharmashop_field_values` (`product_id`, `variant_id`, `field_id`, `option_id`, `num`, `num_end`, `str`) с индексами `idx_option (field_id, option_id, product_id)`, `idx_num`, `idx_num_end`, `idx_str`, `idx_product`. Опции: `field_options` (`alias`, `title`, `color`, `image`, `ordering`). Определение поля: `filterable`, `level` (товар/вариант), `all_categories` + список категорий, `params`.
- **Витринный индекс** `#__dharmashop_product_categories`: строка на пару «товар — категория/бренд/бейдж» **включая родителей**; `state`, `price_sort` (= минимальная эффективная цена), `in_stock`, `sort_order`, `created`, `title_sort`; индексы `(catid, state, …)` под каждую сортировку. Бренды и бейджи — те же строки (`direct = 1`) в своих секциях.
- **Единственная точка сборки списка** — `Site\Model\CategoryModel::productsQuery()` (состояние, доступ категорий, скрытый предок, поиск `filter[search]`, JOIN на `pc`). Фильтр встраивается сюда же: `getProducts`, `getTotal`, подсказки поиска и счётчики видят один и тот же состав.
- **Адрес**: параметры `filter[…]` уже зарезервированы и переносятся сортировкой/видом (`listing.js`); AJAX-замена списка через `format=raw` и события `dharmashop:navigate` / `dharmashop:updated`.
- **Типы полей** — плагины группы `dharmashopfield` (`TypeInterface`), события `onDharmaShopFieldFilterElement` / `onDharmaShopFieldFilterApply` записаны в ARCHITECTURE §6.2 как план.
- **Замеры этапа 0** (`BENCHMARKS_NOTES.md`): список + цена + 3 фильтра по полям — 6–32 мс на 100 тыс.; счётчики — 50–100 мс на поле; рост линейный по числу кандидатов. Предложение E13: счётчики на лету не считать — этот файл его развивает (§6).
- **Правила проекта**: админка нативная; на сайте — только классы Bootstrap, без собственного CSS компонента и inline-стилей (исключения утверждает пользователь, см. §12); минимум JS; скорость — индексируемые столбцы, никаких `JSON_*`, `LIKE '%…%'`, `SELECT *`, больших `OFFSET`.

## 5. Модель данных

### 5.1 Параметры адреса (контракт)

Общий префикс `filter[…]` (как у поиска). Ключи — **алиасы**, а не номера (читаемо, переживает переиндексацию, нельзя перебирать id):

| Параметр | Смысл |
|---|---|
| `filter[search]` | текст поиска (уже есть) |
| `filter[f][<алиас поля>][]=<алиас опции>` | список/чекбокс: значения одного поля — ИЛИ (по умолчанию) либо И (настройка поля) |
| `filter[f][<алиас>][min]=&filter[f][<алиас>][max]=` | число / диапазон (для range — пересечение) |
| `filter[price][min]`, `filter[price][max]` | цена |
| `filter[brand][]=<алиас бренда>`, `filter[badge][]=<алиас бейджа>` | бренд, бейджи (бренд — ИЛИ) |
| `filter[cat][]=<алиас подкатегории>` | сужение по подкатегориям |
| `filter[stock]=1`, `filter[sale]=1` | в наличии, по акции |

Правила разбора (`FilterState`): известные ключи; каждое значение сопоставляется со справочником (неизвестные отбрасываются молча); границы приводятся к числу и зажимаются в допустимый диапазон; **пределы**: не более 12 активных полей, 50 значений на поле, длина адреса — по настройке; пустое состояние равно «без фильтра» (канонический адрес). Состояние сериализуется обратно в **канонический** адрес (порядок ключей стабилен) — по нему ключ кэша и `rel=canonical`.

### 5.2 Используем без изменения схемы
- Поля, значения, опции, диапазоны — `field_values` (+ `field_options`).
- Цена, наличие — `pc.price_sort`, `p.price_max`, `pc.in_stock`.
- Бренд, бейджи, подкатегории — строки `product_categories` в своих секциях/ветках.
- Поиск — существующий подзапрос `m`.

### 5.3 Добавления схемы (по итогам F0 — п. 1 и 2 подтверждены замерами, см. §9.1; схема меняется только после согласования)
1. **Доп. столбец «акция»** в витрине (`products.on_sale` + копия в `pc`, `tinyint`): акции — по флагу, а не по сравнению цен в `variant_prices`; поддерживает `SaleScheduler` и перестройка (по таймеру окончания скидки).
2. **Таблица базового состояния** `#__dharmashop_filter_facets (catid, field_id, option_id, products, PRIMARY KEY (catid, field_id, option_id))` и `#__dharmashop_filter_ranges (catid, field_id, num_min, num_max)` — **подтверждено F0** (живой подсчёт на корне 67–399 мс против 0,4 мс из таблицы). Значения категории, счётчики без выбора и границы ползунка берутся одним индексным чтением. Дополнительно: **покрывающий индекс** `field_values (product_id, field_id, option_id, num)` вместо `idx_product`.
3. **Настройки поля**: `fields.params.filter` (в JSON — это настройки вывода, не данные для поиска): представление по умолчанию, логика ИЛИ/И, сортировка значений, лимит, раскрыто, счётчики. Столбец `filterable` остаётся главным переключателем.
4. Уникальность `(product_id, variant_id, field_id, option_id)` — подтвердить, чтобы счётчики не дублировали товар (иначе `DISTINCT product_id` в подсчёте; в предрасчёте он уже есть).

### 5.4 `FacetIndexer` (если таблица базового состояния принята)
Тот же принцип, что у `Catalog\Indexer`: изменения по товару — относительные (`products ± 1` по строкам `pc` товара) в тех же точках, где обновляется витрина (сохранение, смена состояния/цены, перемещение категории); полная и частичная пересборка — пакетами, командой `reindex` и задачей планировщика; страховка — проверка согласованности (счётчик из таблицы против `COUNT`) в тестах.

## 6. Запрос: условия, значения, счётчики

### 6.1 Условия (`FilterQuery`)
Один источник состава — `productsQuery()` + условия фильтра. Формы условий (выбор формы — по замеру F0, правило: без `Using filesort` на путях листинга и ≤ 80 мс при 3 условиях на 100 тыс.):

```sql
-- список/чекбокс, значения одного поля через ИЛИ
EXISTS (SELECT 1 FROM field_values fv WHERE fv.product_id = p.id AND fv.field_id = :f AND fv.option_id IN (:o1, :o2))
-- логика «И» внутри поля: по одному EXISTS на каждое значение
-- число
EXISTS (SELECT 1 FROM field_values fv WHERE fv.product_id = p.id AND fv.field_id = :f AND fv.num BETWEEN :a AND :b)
-- range (пересечение): fv.num <= :max AND fv.num_end >= :min
-- цена (любой вариант попадает в диапазон)
pc.price_sort <= :max AND p.price_max >= :min
-- наличие / акция
pc.in_stock = 1 / p.on_sale = 1
-- бренд / бейдж
EXISTS (SELECT 1 FROM product_categories b WHERE b.product_id = p.id AND b.catid IN (:brands) AND b.direct = 1)
```
Поле варианта находит товар, если подходит любой из его вариантов (EXISTS не дублирует товары). **Выбор формы по плотности (замеры F0, §9.1):** по оценке плотности условий (доля товаров, из таблицы предрасчёта) — если `(смещение + лимит) / плотность ≤ 30 000`, запрос идёт по индексу сортировки категории (`FORCE INDEX (idx_l_order|price|new|title)` + `EXISTS`) и останавливается на последнем нужном совпадении; для редких условий — обычный запрос, где оптимизатор выбирает ведущее условие по значению поля. Запрос списка защищён подсказкой `MAX_EXECUTION_TIME`; число найденных — через ведущую выборку по самому редкому значению, с потолком, результат — в кэш состояния.

Общее число — `COUNT` с верхним пределом (как сейчас), в AJAX — один раз на запрос.

### 6.2 Значения (что показывать)
`FilterDefinition` категории — какие поля фильтруются (`filterable = 1`, `all_categories` или категория в списке, опубликованы, тип доступен), их опции с алиасами/цветом/картинкой, границы чисел и цены. Читается 1–2 запросами и **кэшируется** (§6.4). «Значения, которые есть в категории» — из таблицы базового состояния (если принята) или одного агрегата по индексу `idx_option`.

### 6.3 Счётчики и каскад (`FacetEngine`)
Режимы (общая настройка + переопределение в модуле): 
- `off` — значения без чисел; пустые скрываются/отключаются **по базовому состоянию** (без каскада);
- `base` — числа базового состояния категории (мгновенно, из предрасчёта/кэша), каскад выключен;
- `live` — каскад: числа и доступность пересчитываются под текущий выбор.

Каскад — стандартная «дизъюнктивная фасетная схема»: числа поля считаются по фильтрам **всех остальных** полей (выбор самого поля не сужает его же значения). Запросов: один общий для всех полей без выбора + по одному на поле с выбором (обычно 1–3 на страницу):

```sql
SELECT fv.field_id, fv.option_id, COUNT(DISTINCT fv.product_id) AS n
FROM field_values fv JOIN (/* кандидаты: productsQuery() без условий этого поля */) c ON c.id = fv.product_id
WHERE fv.field_id IN (:fields) GROUP BY fv.field_id, fv.option_id
```
Защиты: если число кандидатов больше порога (`facet_live_limit`, по умолчанию 20 000), число считается из базового состояния, а ответ помечается «приблизительно» (текст/значок настраивается); при превышении бюджета времени — тот же откат. 

### 6.4 Кэш
Группа Joomla `com_dharmashop_filter`; ключ — канонический адрес состояния + категория + уровни доступа посетителя (если они влияют) + набор запрошенных полей. Значение — массивы значений/чисел. Сброс — при любой записи каталога (товар, цены, остатки, поля, категории): точка вызова рядом с `Indexer`; плюс время жизни `cache_ttl`. Кэш определений полей — отдельный ключ, сбрасывается при правке полей/опций.

## 7. Поведение на сайте

- **Без JavaScript:** GET-форма на адрес страницы; список — обычный вывод; значения/числа приходят из сервера при каждом показе; кнопки «Применить» / «Сбросить» — обычные.
- **С AJAX (реализовано иначе, F5, 2026-10-09):** скрипт запрашивает обычный адрес страницы с параметрами фильтра, из ответа берёт `[data-dharmashop-listing]` и форму фильтра по `id` и подменяет их (сохраняя раскрытые группы и фокус; форма, изменённая во время запроса, не заменяется) — единый вывод сервера, без отдельного JSON и без разметки в JS; облегчённый ответ (модуль + список без шаблона) — возможная оптимизация. Исходный замысел: один запрос `index.php?option=com_dharmashop&task=filter.apply&format=json` + состояние → ответ `{ok, html (фрагмент списка, как format=raw), total, facets {поле: {опция: n}}, price {min,max}, chips, url}`; скрипт заменяет список, обновляет значения в **уже выведенной** форме (включает/отключает/скрывает, переписывает числа) и делает `history.pushState(url)`; `popstate` возвращает состояние. Форма выводится сервером целиком (никакой разметки в JS). Ошибка запроса — обычная отправка формы. Событие `dharmashop:updated` после замены (как сейчас).
- **Применение:** `instant` (по изменению; с задержкой для полей цены и текста) или `button`; на кнопке — число найденных (если счётчики `live`).
- **Активные условия:** «чипы» над списком/в модуле с крестиком и «Сбросить всё».
- **Адрес и SEO:** адрес с `filter[…]` — для пользователя (отправка ссылкой), поисковикам: `noindex, follow` + `rel=canonical` на страницу без фильтра (настройка; по умолчанию вкл.), `rel=nofollow` у ссылок значений в режиме без JS (настройка), пустой результат — страница с кодом 200 и подсказкой «Сбросить фильтр».
- **Вместе с остальным:** сортировка, вид, пагинация («Показать ещё»/бесконечная) сохраняют условия; смена фильтра сбрасывает `start`.
- **Доступность:** `fieldset`/`legend` на группу, `aria-controls` у раскрывающихся блоков, `aria-live` для числа найденных, управление клавиатурой в dropdown/offcanvas (штатное Bootstrap).

### 9.1 Результаты F0 (2026-10-09)

Стенд `dev/bench` (таблицы `bn_*` того же MySQL 8.4.3, `innodb_buffer_pool_size` = 128 МБ — ниже обычного рабочего, цифры консервативны), 100 / 10 000 / 100 000 товаров, 1,94 млн строк `field_values`, 457 тыс. строк витрины. Сводные таблицы — `docs/BENCHMARKS_FILTER.md` (генерируется `php dev/bench/filter.php report`); скрипты — `dev/bench/filter.php` (формы условий, счётчики, предрасчёт), `filter2.php` (выбор формы по плотности), `filter3.php` (редкие условия, глубокая страница, подсчёт).

**Выводы**
1. **Форма «F» — обход индекса сортировки категории с `FORCE INDEX` и `EXISTS` по условиям — выигрывает почти везде**: список на корне каталога 1,5–20 мс против 40–130 мс у обычных `EXISTS`/ведущей выборки (цена широкая: 3,7 мс против 408 мс). Оптимизатор сам выбирает её плохо: сортирует десятки тысяч подходящих строк (`filesort`). Слабое место F — **редкое условие** (0,1 % и реже; пустой результат): обход читает категорию целиком до 24 совпадений — 4–15 мс, на глубокой странице (смещение 1200) при условии 1 % — 14,7 мс; там обычный запрос (и ведущая выборка по редкому значению) быстрее: 0,5–2 мс.
2. **Правило выбора формы по плотности** (оценка — доля товаров, имеющих значение, из таблицы предрасчёта; для нескольких условий — произведение, для цены — доля диапазона от границ): `F`, если **(смещение + лимит) / плотность ≤ 30 000** строк просмотра; иначе обычный запрос (планировщик выбирает ведущее условие сам). На замерах это даёт ≤ 20 мс во всех сценариях. Подстраховка: подсказка `MAX_EXECUTION_TIME` у запроса списка и откат на другую форму при превышении.
3. **Покрывающий индекс `field_values (product_id, field_id, option_id, num)` вместо `idx_product (product_id, field_id)`**: `EXISTS` без обращения к строке; запросы с несколькими условиями ускоряются в 3–5 раз (89 → 16 мс; 65 → 20 мс; 58 → 9,5 мс). Размер: 58,6 МБ вместо 46,6 МБ (+12 МБ на 100 тыс. товаров); построение на 100 тыс. — 1,6 с.
4. **Подсчёт значений «живьём» на базовом состоянии слишком дорог**: одно поле на корне 67 мс, шесть полей 399 мс, поле варианта с `DISTINCT` 182 мс, границы числа 120 мс. **Таблица предрасчёта подтверждена**: чтение всего базового состояния категории 0,3–0,4 мс (в 1000 раз быстрее); полная сборка на 100 тыс. — 4,3 с (159 тыс. строк, 44 строки на товар); сопровождение при изменении товара — 1,5 мс на 10 тыс. и 15,7 мс на 100 тыс. товаров.
5. **Каскад (числа под выбор) укладывается в бюджет**: 5 полей при выбранном бренде — 43 мс на корне и 10–18 мс в категориях; при трёх выбранных условиях 8–22 мс. Порог кандидатов проверяется за 1–2 мс. Границы цены из индекса витрины — 0,3 мс.
6. **Подсчёт найденных с потолком:** через ведущую выборку по значению 0,3–9 мс (плотное условие 10 %: 9 мс против 46 мс обходом); при нескольких плотных условиях 25–50 мс (с покрывающим индексом — вдвое быстрее); потолок 1 001 вместо 10 001 — 2,5 мс. Предлагается: потолок по настройке (по умолчанию 10 001, «10 000+»), подсчёт через ведущую выборку, результат — в кэш состояния (одно и то же число нужно списку, пагинации и ответу AJAX).
7. **Согласованность:** формы A / B / C / D / F дают одинаковый состав страницы на всех сценариях (проверено).

**Решения по итогам F0 (ПРЕДЛОЖЕНО, подтверждает пользователь)**
- Таблицы `filter_facets` (счётчики базового состояния) и `filter_ranges` (границы чисел) — **делаем**; сопровождение в тех же точках, что витрина (`Indexer`).
- Покрывающий индекс `field_values` — **делаем** (заменяет `idx_product`; миграция — удалить старый после создания нового).
- Ведущее условие и форма «F» с правилом плотности — **закладываем в `FilterQuery`**; без сортировки по релевантности (при поиске порядок задаёт `m.score`: ведущая выборка по поиску).
- Условие «акция» — отдельный столбец витрины (`on_sale`), по флагу; решается на F6.
- Оговорка: данные синтетические (равномерные значения, кроме бренда); независимость условий в оценке плотности — допущение; «плохие» реальные распределения проверить на F8.

## 11. Безопасность и надёжность

- Только известные параметры; алиасы сопоставляются со справочником; числа — `float`/`int` с зажимом; значения в SQL — только привязкой (`bind`); имена столбцов/таблиц — константы.
- Пределы §5.1 защищают от «взрыва» запроса; живой подсчёт — под порогом кандидатов и бюджетом времени; AJAX-запрос ограничивается числом запросов на сессию (как у подсказок поиска).
- Ответ JSON не содержит данных, недоступных посетителю: состав — через `productsQuery()` (доступ категорий, скрытый предок, состояние).
- Ошибки не раскрывают SQL; в журнал — тип исключения (`com_dharmashop`).
- Кэш: ключ включает всё, от чего зависит состав (категория, состояние, доступ).

## 12. Что решаем (ПРЕДЛОЖЕНО — подтвердить или поправить)

1. **Ползунок цены и образцы цвета** требуют либо небольшого CSS модуля (по образцу исключения для мини-корзины C67: файл `mod_dharmashop_filter/media/css/filter.css`, отключаемый, на переменных Bootstrap), либо скрипта, который выставляет размеры/цвета (`style` из JS допустим правилами). **Предложение:** без CSS — два штатных `form-range` и поля ввода, цвета — из JS; CSS-исключение запрашиваем, только если вид окажется неприемлемым.
2. **Счётчики по умолчанию:** `base` (быстро, числа без каскада), `live` — включается настройкой с порогом кандидатов. Подтвердить.
3. **SEO страниц с фильтром:** `noindex, follow` + canonical на страницу без фильтра по умолчанию; индексируемые «чистые» адреса популярных сочетаний — позже.
4. **Логика мультивыбора:** ИЛИ внутри поля, И между полями (как в магазинах); для отдельного поля — переключатель «И».
5. **Варианты:** товар подходит, если подходит любой его вариант (как в ARCHITECTURE §5.5); «строго в одном варианте» — позже.
6. **Область:** фильтр на страницах каталога, категории, бренда, бейджа и поиска (общий состав списка); отдельный экран «Фильтр» в админке не нужен — настройки в магазине, поле и модуле.

Тесты (по плану «тесты — в конце», но заготовки пишутся вместе с кодом): разбор `FilterState` (границы, мусор, пределы), SQL условий (число, range, И/ИЛИ), согласованность счётчиков с `COUNT`, совместимость с поиском и сортировкой, пустые состояния.

## 14. Риски

1. **Каскад на широких категориях** — основной риск скорости; лечится порогом кандидатов, кэшем и режимом `base`; решается замером F0.
2. **Согласованность предрасчёта** (если таблица базового состояния принята) — страховка `reindex` и проверка в тестах.
3. **Поля уровня «вариант»** — подсчёт товаров, а не вариантов (`DISTINCT`), иначе числа завышены.
4. **Много значений у поля (тысячи)** — предел значений и поиск внутри списка; для чисел — диапазон, а не перечень.
5. **Совместимость с типами-плагинами** — контракт `FilterTypeInterface` определяется на F7, до этого работают встроенные типы (list, checkbox, number, range).

## 15. Метатовары (проектное условие, 2026-10-09)

Пользователь планирует «метатовары» (составной товар, набор или группа товаров; модель определяется отдельно). Фильтр проектируется так, чтобы они подключались без переписывания:

1. **Единица фильтра — строка `products` (`product_id`).** Условия (`FilterQuery`), счётчики (`FacetEngine`) и предрасчёт (`FacetIndexer`) работают по `product_id` и `product_categories`, не по типу товара. Метатовар — обычная строка `products` со своими привязками к категориям и значениями полей.
2. **Значения метатовара агрегируются в его собственных `field_values`.** Что «поднимать» из дочерних товаров (объединение значений списков, минимум/максимум чисел и цены) — решение модели метатоваров; фильтр читает готовые строки, поэтому вычисление выполняет сохранение метатовара, а не запрос фильтра.
3. **Хук пересчёта.** Любое изменение дочернего товара пересчитывает агрегаты метатовара и затем вызывает `FacetIndexer::begin()/end()` для затронутых `product_id` (родитель и дочерние) — тот же вызов, что в `ProductModel::save/delete/publish`; нового механизма не нужно.
4. **Скрытые дочерние товары** не попадают в список категории (состав задаёт `productsQuery()`), но их значения могут входить в агрегаты родителя; счётчики по ним не считаются.
5. **Цена метатовара** — диапазон `price_min…price_max`, как у товара с вариантами; условие цены фильтра уже работает по правилу «подходит любой вариант».
6. **События (при необходимости):** `onDharmaShopFilterCollect` (дополнительные источники фильтра) и `onDharmaShopFilterQuery` (дополнительные условия) вводятся вместе с моделью метатоваров и регистрируются в `SHORTCODES.md`.

## 16. Посадочные страницы фильтра (план, ПРЕДЛОЖЕНО пользователем 2026-10-09, C85)

Результат фильтра можно сделать полноценной SEO-страницей и вывести в меню. Для этого — отдельный компонент-сущность «Посадочные страницы» (рабочее имя `com_dharmashop_landing`, пакетное расширение; имена уточняются при проектировании).

1. **Сущность.** Посадочная страница = сохранённое состояние фильтра (`FilterState`: категория-источник + условия полей/цены/бренда/бейджей) + собственные данные, как у категории: название, алиас, картинка, краткое и полное описание (редактор), SEO-заголовок/описание/robots/canonical, состояние, доступ, порядок, дополнительные поля (по образцу полей категории).
2. **Меню.** Тип пункта меню «Посадочная страница» (как у категории/бренда): адрес — обычный ЧПУ-адрес пункта, без `filter[…]` в строке; список товаров строится из сохранённого состояния тем же `CategoryModel::productsQuery()` + `FilterQuery`; посетитель может уточнять выбор фильтром поверх сохранённого (дополнительные условия переходят в `filter[…]`, такая страница — `noindex`, как сейчас).
3. **SEO.** Страница индексируется (в отличие от фильтра с параметрами), `canonical` на себя, попадает в карту сайта и структурированные данные; страницы с теми же условиями, но не посадочные, получают `canonical` на посадочную страницу, если она существует (снимает дубли).
4. **Создание.** В админке: «Сохранить фильтр как посадочную страницу» из списка товаров с применённым фильтром либо форма с выбором условий теми же определениями фильтра (`FilterDefinitionLoader`); число товаров и пустой результат показываются сразу.
5. **Сопровождение.** Условия хранятся по алиасам/идентификаторам значений; при удалении поля или значения страница помечается «устарела» (не 404), в админке предупреждение; счётчики и кэш — общий `FilterCache`.
6. **Подробный план — `docs/LANDING.md` (форма «отдельная сущность» подтверждена пользователем 2026-10-09).**
7. **Согласование.** Схема (таблица страниц), события и подстановки — сначала в `DECISIONS.md`/`SHORTCODES.md`; до реализации обязателен ответ пользователя по имени компонента и по связи с категориями (виртуальная категория или отдельная сущность).
