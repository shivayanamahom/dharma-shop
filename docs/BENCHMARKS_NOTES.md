# Замеры схемы: выводы и оговорки

## Финальный фильтр: реальные модели, 2026-10-11

**Этот раздел описывает финальный PHP-код фильтра. Таблицы этапа 0 ниже исторические и не заменяют эти результаты.**

Методика: `php dev/bench/filter-final.php` поднимает реальный Site CategoryModel, FilterState/Query, GroupListing, ScopedFacets и FacetIndexer. Отдельный случайный префикс БД; действующий каталог не размножается. Размеры 100 / 10 000 / 100 000, по пять типизированных значений на товар (500 000 на большом размере), 4 участника группы + 1 независимый товар на каждые 5. Проверяются две/три оси фильтра, корень/категория, products/groups: 24 случая. Ожидаемый total вычисляется независимой формулой; каждая выдача содержит min(24,total), FacetIndexer verify проходит на всех размерах. Таблицы удаляются в finally.

Cold означает сброшенный кэш фильтра, **не холодный диск/процесс/OPcache**. Измеряются getTotal+getProducts (включая пакетное обогащение групп), затем getFacets(live). Warm — новая модель с тем же состоянием, 1 прогрев + 7 образцов; p95 при 7 образцах фактически максимум и не годится как промышленная статистика. В эти цифры не входят attachCardData, шаблон/HTML, сеть, изображения и отрисовка браузера. Один поток, локальная машина, без конкурентных записей.

Итог: одиночные отфильтрованные товары при повторном обращении укладываются в исходную цель 80 мс в измеренных случаях. **Для всех групповых случаев цель 80 мс не достигнута.** На тяжёлой групповой категории первый запрос вместе с фасетами занимает до 2,32 с, повторный — 241–406 мс. Нельзя переносить прежнее утверждение о почти плоской скорости схемы на этот путь. Большой live-каскад ограничивается бюджетом: при превышении возвращает обозначенные базовые/неполные данные. Это ограничивает нагрузку, но ослабляет точность доступности значений.

Что исправлено по итогам профилирования:

- У упорядоченного товарного списка реальный ведущий product_categories FORCE INDEX + STRAIGHT_JOIN. EXPLAIN выбранного category/new пути подтверждает обход idx_l_new и p eq_ref, без filesort.
- Убрана лишняя проверка закрытых предков на каждый товар только при кэшированном доказательстве полной публичности каталога; закрытый каталог сохраняет ACL-проверки.
- Total кэшируется с составом/состоянием/cap. Representative выбирается ROW_NUMBER один раз вместо повторного антизапроса на каждого участника.
- Состав групп на странице обогащается ограниченными пакетами; проверка категорий группы идёт по её связям для подходящих кандидатов, без предварительной материализации всех участников ветки.
- У фасетов единый бюджет и пакетные запросы, базовый результат ленивый. Fallback не выдаёт неизвестность за ноль.

Групповая сортировка закономерно использует оконную сортировку/временную таблицу; EXPLAIN без filesort не является выполненным условием для этого пути. Следующая оптимизация — отдельный план выборки групп/перенос селективного candidate set перед category/group joins и дополнительные агрегаты, с повторением same-member/ACL тестов.

## Что нашли

1. **Фильтр на широкой категории растёт почти линейно по числу кандидатов:** корень каталога + цена + 3 фильтра — 0,3 мс (100) → 1,7 мс (10 тыс.) → 32 мс (100 тыс.). На 1 млн товаров ожидаем порядка 300 мс. Для заявленных «100 и 100 000+» это нормально; если понадобится больше — запасной приём из ARCHITECTURE.md (сначала выбрать кандидатов по самому селективному полю).
2. **Счётчики значений фильтра («Бренд (12)») дороги: 50–100 мс на одно поле на 100 тыс. товаров** (в корне каталога без фильтра 68 мс, с выбранным цветом 102 мс). У фильтра с 8 полями на лету это 0,5–0,8 с на каждый запрос. **Вывод: счётчики нельзя считать при каждом показе.** Нужно либо отключаемое кэширование по ключу «категория + выбранные значения», либо предрасчёт счётчиков «без фильтра» для категории в отдельной таблице при переиндексации. Предложено решение E13 в `DECISIONS.md`.
3. **Админка:** глубокая страница списка (`OFFSET` ≈ 99 000) — 69 мс и поиск `LIKE '%…%'` по названию — 66 мс на 100 тыс. товаров. Рост линейный, для админки терпимо; поиск в админке можно перевести на FULLTEXT-таблицу `search`, глубокие страницы — штатное поведение Joomla.
4. **`L2(12) / order` сортирует (`filesort`)** — планировщик выбрал другой индекс для категории с 1 тыс. товаров; время 1 мс, не влияет. Стоит перепроверить на реальных данных и при необходимости подсказать индекс (`FORCE INDEX`) в `ListingQuery`.
5. **Размер данных:** 100 тыс. товаров ≈ 1,1 ГБ (из них `field_values` 384 МБ, `products` 270 МБ — основная часть это тексты описаний, `product_categories` 191 МБ). `product_categories` содержит ~5 строк на товар (лист + 3 предка + дополнительная категория) — приемлемая цена за скорость листинга.

## Оговорки (не считать результаты «боевыми»)

- Данные **синтетические**, распределения простые (CRC32): у брендов есть перекос, у остальных значений нет. Реальные каталоги могут быть менее удобными.
- `innodb_buffer_pool_size` = **128 МБ** при 1,1 ГБ данных: часть чтений шла с диска, результаты скорее консервативны, но это и не «холодный» запуск: перед замером 2 прогрева.
- Один поток, без параллельной нагрузки, без блокировок от записи.
- Замеряется **только база** (через драйвер Joomla), без PHP-кода, отрисовки и сети.
- Для запросов фильтра подобраны конкретные значения (бренды 3–4, материалы 33/36, цвета 130/131); нужен ещё прогон с «плохими» значениями (самое частое значение, комбинации, дающие много кандидатов).
- Не измерены: сохранение товара и перестроение индекса, массовые операции, перемещение категории (перестройка поддерева), корзина и заказы.
- Сравнение с RadicalMart на 10 и 50 тыс. товаров сделано отдельно — см. `BENCHMARKS_RM.md` и `BENCHMARKS_RM_NOTES.md`.
