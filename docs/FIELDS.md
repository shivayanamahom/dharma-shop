### Типы стандартного плагина

В просмотренном `standard.xml` версия плагина **2.1.5**. Он объявляет семь типов:

- одиночный/множественный список;
- набор флажков;
- короткий текст;
- многострочный текст;
- редактор;
- число;
- числовой интервал с двумя границами.

Это один плагин с несколькими типами, а не отдельное расширение на каждый тип. Общий механизм компонента не ограничен этим набором. В стандартном плагине не обнаружены типы галереи и файла; наличие их у других плагинов в рамках исследования не проверялось.

### Конкретные уроки для нашего кода

1. Общие правила поля и поведение типа нужно разделить. Название, категории, доступ и порядок не должны повторяться в каждом плагине.
2. Возможности типа лучше объявлять явно: фильтруется ли он, допускает ли несколько значений и может ли быть осью вариантов. Форма и серверная проверка используют одно описание возможностей.
3. В просмотренном методе вывода стандартного плагина проверка пустоты отбрасывает и `0`; в фильтре границы тоже проверяются на пустоту. У нас `null`/пустой ввод, ноль и «Нет» должны различаться при вводе, сохранении, фильтрации и выводе. Это наблюдение по исходнику, не воспроизведённый браузерный дефект.
4. У нас уже принята своя индексируемая схема: не заменять её сериализованными значениями товара или строками ID категорий.

## 2. Что уже есть у Dharma Shop

В `com_dharmashop/admin/sql/install.mysql.utf8.sql` созданы:

- `fieldgroups` — название, алиас, порядок, состояние, блокировка редактирования;
- `fields` — группа, тип, способ хранения, уровень товар/вариант, назначение всем категориям, фильтрация, сортировка, вывод в списке/странице, обязательность, единица, доступ и настройки типа;
- `field_options` — стабильный ID варианта выбора, алиас, название, цвет, изображение, порядок;
- `category_fields` — отдельные связи категории и поля;
- `field_values` — индексируемые `option_id`, `num`, `str`;
- `field_texts` и `field_media` — длинные тексты и файлы отдельными строками;
- `product_axes` — заготовка связи осей будущих вариантов товара.

Админка групп реализована (`view=fieldgroups`, `view=fieldgroup`). Формы бизнес-полей, реестра типов и плагина типов ещё нет. Классы в `admin/src/Field` — элементы форм Joomla, не готовая подсистема каталожных полей.

**Действующая галерея товара уже реализована** через `GalleryRepository` и `field_media.field_id=0` (C19). Не создавать вторую галерею и не переносить существующие файлы автоматически при добавлении реестра. Сначала предусмотреть совместимость с этой служебной галереей; возможное объединение — отдельная миграция после согласования.

### Поставляемый плагин стандартных типов

Группа уже предусмотрена: `dharmashopfield`. Точное имя элемента плагина, классов и файлов пока не утверждено.

- Регистрирует типы с понятными подписями.
- Для каждого типа сообщает способ хранения, кратность, допустимый фильтр, сортировку и поддержку осей вариантов.
- Даёт XML настроек и элемент заполнения товара, правила нормализации/валидации, вывод значения.
- Пользуется общим хранилищем компонента. Разработчик обычного нового типа не должен заново писать сохранение товара, SQL связей и загрузку группы.
- Дополнительный тип со специальным хранением или фильтром подключается через отдельный согласованный контракт; произвольная SQL-строка из пользовательской настройки не допускается.

Предлагаю регистрацию через уже запланированное `onDharmaShopFieldTypesCollect` и объект обработчика типа. Для получения формы/кодирования/вывода можно обращаться к найденному обработчику, а не рассылать событие всем плагинам для каждого значения. **Это проект интерфейса**, не действующий API: остальные события из §6.2 пока остаются зарезервированными, их точные аргументы и взаимодействие с обработчиком нужно определить перед кодом.

В админке пользователь выбирает **тип поля из единого списка**. Поставщик типа показывается справочно; выбирать отдельно плагин и затем его подтип не требуется. ID типа стабилен, принадлежность провайдеру определяется реестром; дубли ID должны выдавать понятную ошибку.

## 5. Правила, которые нужно принять перед реализацией

- **Категории:** предлагается объединять поля основной и дополнительных товарных категорий, удаляя дубли по ID. Бренды/бейджи не подмешивают характеристики автоматически. При выводе в конкретной категории фильтр берёт поля этой категории; товарная форма и фильтр списка имеют разный контекст.
- **Наследование:** назначение категории и применение к её потомкам должны быть явными. Текущая `category_fields` хранит только связи, поведение наследования ещё не реализовано. Предлагается переключатель наследования в настройках поля; без необходимости не добавлять сложную систему исключений.
- **Ноль/Нет:** отсутствие значения хранится отдельно от нуля. «Да/Нет» лучше хранить числом `0/1` и показывать выбор с отдельным состоянием «Не указано». Обязательное поле допускает «Нет», если это полноценный ответ.
- **Смена типа:** при наличии значений запретить смену способа хранения и несовместимую смену типа; изменение только через явную миграцию. Нельзя доверять `store` из POST: оно определяется зарегистрированным типом.
- **Опции:** смена подписи/порядка не меняет ID. Используемую опцию нельзя незаметно удалить с потерей данных; форма сообщает число использований и требует отдельного действия замены/очистки.
- **Отключённый плагин:** значения остаются. Админка показывает «Тип недоступен», изменение этих значений блокируется. Сохранение других свойств товара не удаляет их. На сайте недоступный тип не ломает всю страницу; он исключается из соответствующего вывода/фильтра с записью диагностики.
- **Неприменимые поля:** смена категории, состояния или доступа скрывает поле, но сама по себе не очищает сохранённые значения. Отсутствующий элемент формы не равнозначен команде очистки.
- **HTML:** простой текст экранируется; HTML редактора проходит штатную фильтрацию Joomla. Ссылка и файл проверяются отдельно; файлы чистятся существующим механизмом ссылок, не удалением всей папки.
- **Сортировка:** разрешается только однозначный ключ на товар. Мультивыбор и значения нескольких вариантов нельзя включить в сортировку одним флажком без принятого правила агрегации и индекса. Сам факт столбца `sortable` ещё не обеспечивает быструю сортировку.

## 6. Набор и порядок реализации

**Первый проход:** короткий текст, число, одиночный список, мультивыбор, «Да/Нет». Мультивыбор имеет общее хранение `option_id`, независимо от представления списком или флажками.

**Следующий проход:** многострочный текст, редактор, изображение/галерея и файл с учётом существующей загрузки. Это сохраняет набор приёмки этапа 2. URL, дата, видео, структурированные таблицы — дальнейшие типы при потребности. Интервал как значение товара требует отдельной модели двух границ; обычный фильтр числа «от/до» не требует интервала в данных товара.

1. Утвердить правила из §5 и минимальный контракт типа.
2. Реестр + поставляемый плагин + экран «Поля», настройки и опции. Группы уже реализованы, C50 добавил назначение товарам или категориям.
3. Динамическая вкладка «Характеристики» товара, проверка и сохранение первых типов в существующие таблицы.
4. Вывод в карточке и полной странице через нашу библиотеку макетов; единая загрузка данных и настройки показа.
5. Длинные тексты и медиа; фильтр списка/модуль, затем замеры на большом каталоге.

Проверки реализации: `0`, «Нет», пустое значение; обязательность; обе границы числового фильтра; одиночный/множественный выбор; сохранение черновика при перезагрузке формы; дополнительные категории; отключение плагина; сохранение товара со скрытым полем; удаление используемой опции; конфликт типов; ACL; отсутствие запросов на каждую карточку. Производительность подтверждается замерами, не названием архитектуры.

## 9. Назначение товарам или категориям (C50)

Пользователь попросил дополнительные поля и у товаров, и у категорий. Это расширяет прежний план, ограниченный характеристиками товаров.

### Реализовано сейчас

- У группы выбор «Для товаров / Для категорий», по умолчанию «Для товаров».
- В списке групп колонка и фильтр назначения. Создание из отфильтрованного списка наследует выбранное назначение.
- По уточнению пользователя назначение списка по умолчанию — «Для товаров», включая возврат после «Очистить». «Все» остаётся явным выбором (`*`), категория и явный выбор всех сохраняются в сессии. Панель параметров поиска при рендере раскрыта всегда штатным Searchtools, как в списке товаров; собственного JS/CSS нет.
- В `fieldgroups` и `fields` добавлен `target varchar(16) NOT NULL DEFAULT 'product'`; допустимые значения `product`, `category`. У группы допустимость проверяется сервером. Формы полей пока нет.
- Группа с полями не меняет назначение, даже если все поля скрыты/в корзине. Изменение названия и состояния продолжает работать.
- Порядок групп отдельный для каждого назначения. Перетаскивание доступно при фильтре одного назначения; числовой порядок в форме доступен по штатным правам изменения состояния.
- Установочный скрипт пакета добавляет отсутствующие столбцы к существующим таблицам без удаления записей. Повторная установка не добавляет их снова. Все прежние поля/группы получают `product`, установка с нуля использует обновлённый SQL. Исключение из прежнего совета DEVELOPMENT о деинсталляции при смене схемы: здесь применяется аддитивное обновление.

### Следующие шаги подсистемы полей

1. В форме поля — назначение и только группы того же назначения. Поле без группы имеет собственный `target`. При сохранении сервер проверяет совместимость; по умолчанию наследовать назначение выбранной группы, несовместимое поле не переносить автоматически.
2. `target=product` заполняется у товаров, `level=2` относится только к их вариантам. `target=category` заполняется в форме категории; осей вариантов, цен и товарной обложки у него нет.
3. Типы ввода, нормализация и макеты значений общие. Применимость, права записи и хранилище выбираются по назначению.
4. `category_fields` остаётся таблицей применимости определений: товарные поля назначаются товарам категории, поля категории — самой записи. `all_categories` задаёт общий охват внутри соответствующего назначения. Это не таблица значений категории.
5. Для значений категории добавить отдельные таблицы простых значений, текста и медиа с `category_id`, используя уже принятую схему `option_id`/`num`/`str`. Конкретный SQL и адаптер сохранения ещё не реализованы; хранить категорию как фиктивный `product_id` нельзя.
6. Вывод `in_card` и `in_page` относится к карточке/странице выбранного назначения. Поле категории не должно становиться характеристикой каждого её товара или участвовать в товарном фильтре без отдельного согласованного механизма.
7. После появления записываемых значений категории учесть их медиа в `ImageCleaner` и WebP-обработке, удаление значений при удалении категории и ACL штатного ресурса категории. Сейчас новых записываемых медиа/значений категории нет.

## 12. Начальный набор типов и организация файлов — предложение

Пользователь 2026-10-07 запросил начальные типы: чекбокс, список, текст, редактор, число и, возможно, диапазон. Повторно прочитана установленная копия `nrk.steel/plugins/radicalmart_fields/standard`: один плагин, XML каждого типа в `forms/products`, основная обработка нескольких типов в общем `src/Extension/Standard.php`, дополнительные классы элементов формы/фильтра. Это наблюдение о локальной копии, её код не переносился.

Для Dharma предлагается один поставляемый плагин базовых типов группы `dharmashopfield`, внутри отдельный обработчик каждого типа. Например, текст: `src/Type/TextType.php` (возможности, нативный FormField, проверка/нормализация), `forms/text/settings.xml` (настройки определения), `layouts/text/default.php` (вывод). Так код, XML и макеты остаются в обычных зонах расширения Joomla; отдельные папки внутри forms/layouts группируют файлы по типу. Точное имя плагина и ID типов ещё не зафиксированы; это не существующее API и не готовые файлы. Настройки назначения, группы, доступа, состояния, применимости и показа в карточке/странице остаются в компоненте.

Начальные возможности:

- Чекбокс: нужно различать одиночный флажок Да/Нет и набор опций; представление уточняется перед реализацией. Явное «Нет» не равно незаполненному значению.
- Список: выбор одной/нескольких стабильных опций, названия опций не используются как ключи значений.
- Текст: длина, подсказка, значение по умолчанию; обычный текст экранируется при выводе.
- Редактор: штатный редактор Joomla, HTML проходит разрешённую политику фильтрации; в краткую карточку богатый текст по умолчанию не выводится.
- Число: границы, шаг, точность, единица; ноль — допустимое значение.
- Диапазон как значение: две числовые границы с проверкой порядка. Текущая схема имеет один `num`, поэтому индексируемое хранение интервала требует отдельного согласованного дополнения; не сохранять интервал строкой или JSON. Диапазон фильтра по обычному числу — иной механизм, отдельного типа значения для него не требуется.

Следующий конкретный шаг после согласования: реестр/обработчики типов и нативная форма определения поля, затем заполнение и сохранение значений товаров/категорий, затем вывод в карточках и на страницах. В этом исследовании код, база и пакет не менялись.

## 13. Реализовано: определения базовых полей (C53)

Пользователь согласовал сначала создать все экраны, затем дорабатывать обработку каждого типа. Диапазон — самостоятельная характеристика **с двумя числовыми границами**, не поле цены. Пункт меню «Поля» открывает нативные список и форму Joomla; доступны создание/сохранение/отмена, публикация/архив/корзина/check-in, поиск, фильтры назначения и состояния, пагинация и порядок. По умолчанию список показывает поля товаров, Searchtools открыт. Назначение поля фиксируется после создания; по C54 тип тоже фиксируется после первого сохранения. Группа проверяется сервером на совпадение назначения. Удаление поля со значениями или осями вариантов запрещено.

Поставляется отдельный плагин **`plg_dharmashopfield_basic`**, установленный в `plugins/dharmashopfield/basic`. Типы `checkbox`, `list`, `text`, `editor`, `number`, `range`. Для каждого — класс `src/Type/<Имя>Type.php` и XML `forms/<id>/settings.xml`. Пока это обработчики **настроек определений**, а не готового ввода/вывода значений. Макеты значений не создавались.

В компоненте `Administrator\Fields\TypeRegistry` и `TypeInterface`. Событие `onDharmaShopFieldTypesCollect` передаёт изменяемый объект `registry`; включённые плагины вызывают `register(TypeInterface)`. Реестр собирается один раз за запрос, после события закрывается; повторяющиеся/недопустимые ID отвергаются. Контракт типа: `id()`, `label()`, `store()`, `settingsPath()`, `normalizeSettings(array)`. Остальные события подсистемы полей пока не реализованы. Плагин автоматически включается при первом добавлении в пакет; обновление сохраняет ручное отключение. Недоступный тип нельзя сохранить, записи при отключении провайдера не удаляются.

По уточнению C55 у определения **ровно две вкладки**: «Основное» (обязательность, единица, настройки выбранного типа и варианты выбора) и «Отображение» (список/полная страница). Отдельные вкладки «Настройки типа» и «Применение» убраны. По C54 назначение, тип и группа находятся в рамке сайдбара «Назначение и тип» для всех типов полей. Во второй рамке «Применение» — все или выбранные категории; затем рамка публикации со состоянием, порядком, доступом и ID. Назначение **и тип** фиксируются сразу после первого сохранения, даже без значений: Form отключает селекты и фильтрует POST, Table отвергает изменения независимо от формы. Группу можно менять в рамках назначения. Все XML типов загружаются в одну Form; штатный `showon` показывает в «Основное» только настройки выбранного типа без собственного JS/CSS. XML находится в плагине, общие настройки в компоненте.

Настройки первого прохода:

| Тип | Доступно в определении |
|---|---|
| Чекбокс | Одиночный Да/Нет или набор вариантов, состояние по умолчанию |
| Список | Один/несколько вариантов, редактируемые опции |
| Текст | Длина до 190 символов, подсказка, значение по умолчанию |
| Редактор | Высота штатного редактора |
| Число | Допустимые минимум/максимум, шаг, точность, единица |
| Диапазон | Допустимые минимум/максимум для будущих границ, шаг, точность, единица, подписи двух границ |

Опции — стабильные строки `field_options`, их ID сохраняются при переименовании. Список/набор флажков требует хотя бы одну опцию; проверяются названия, уникальные алиасы и принадлежность ID. Используемую опцию удалить нельзя. Категории сохраняются в `category_fields`, только секция `com_dharmashop`; пустой ограниченный набор запрещён. Настройки выбранного типа записываются в `fields.params` (это конфигурация, не значения товара); настройки других типов отбрасываются.

Сохранение: до `AdminModel::save` проверяются опции/категории; таблица проверяет тип, группу, алиас и настройки. После штатного `Table::store` опции/связи обновляются отдельной транзакцией. При её ошибке определение компенсируется прежним снимком либо удаляется новая запись; отдельное сообщение сообщает о невозможности компенсации. Это учитывает `LOCK TABLES` Joomla; расширения, подписанные на нативное after-save, пока не должны считать значения/индекс поля готовыми. Существующие товары/категории не перезаписывались; тестовые поля не создавались.

**Ограничение этапа:** можно создавать и редактировать определения всех типов. Их значения пока не заполняются в товарах/категориях и не выводятся в карточках. Для диапазона записан `store=range` как описание будущего хранилища; колонок двух границ значений ещё нет. Ввод, валидация конкретного значения, хранение категорий, возможности фильтра/вариантов и макеты значения реализуются далее по типам. Схема БД в C53 не менялась.

## 15. Контексты вывода (C57, 2026-10-07)

Вкладка «Отображение»: отдельные нативные fieldset «Список товаров», «Полная страница», «Фильтр», «Вариативность». Первые два содержат независимые переключатели «Загружать поле / Выводить поле» и выбор формата: строка через запятую, список, картинка, картинка и название. `load_card/page` и `format_card/page` хранятся в конфигурации `fields.params`, `in_card/page` — прежние индексируемые флаги. Для прежних определений загрузка по умолчанию включена, формат comma, флаги вывода сохраняются. Общую конфигурацию нормализует компонентный `Fields\DisplaySettings`, настройки типа — провайдер; они сохраняются вместе.

`filterable` теперь сохраняется из формы, но интерфейса фильтра ещё нет. `params.variation` — резерв будущего выбора вариантов: только list; для остальных типов форма показывает отключённый переключатель, сервер всегда нормализует в 0. Одновременно виден ровно один переключатель. У поля внутри params нативное условие `.type:list` ссылается на корневой тип; условие `type:list` там искало params.type и оставляло лишнюю строку видимой (исправлено). Это не меняет `level`, не создаёт варианты/оси и не включает отсутствующий движок.

`Site\Support\ProductFields::attach` получает определения и значения одной страницы товаров пакетно. Учитываются опубликованные поля/группы, уровни доступа, назначение product, уровень 1 и применимость через индекс категорий (основная/дополнительные и предки). Чтение значений ограничено ID товаров текущей страницы и ID загружаемых полей, `variant_id IS NULL`; никаких SQL JSON-функций, запросов по карточке или SQL в макетах. Опции берутся из field_values + field_options; текст/число/одиночный чекбокс — str/num, редактор — field_texts. 0 и Нет сохраняют смысл. Число форматируется без преобразования в float. Диапазон ожидает отдельного хранилища двух границ и здесь не выдумывается.

Контракт `item.fields[alias]`: объект `id, alias, title, type, show, format, values`; значение — `text, image` (безопасный URL), `html` (редактор). Если загрузка выключена, поле не попадает в данные. Если вывод выключен — заполненное поле остаётся в данных для своего макета, стандартный макет его скрывает. Пустые значения не порождают dt/dd.

Файловые макеты `components.dharmashop.fields.default` и `fields.value` установлены пакетом в layouts/components/dharmashop/fields и переопределяются шаблоном. Общая разметка dl/div/dt/dd и Bootstrap. Для списочного формата внутри dd используется ul/li. Форматы изображения используют image опции; без изображения показывают название. Текст экранируется, HTML редактора очищается Joomla InputFilter по разрешённым тегам/атрибутам, без скриптов и inline-стилей.

Загрузка подключена в CategoryModel::attachCardData (также продукты брендов/бейджей) и ProductModel::getItem. Вывод подключён к полной странице товара, grid всех трёх папок карточек товаров и заготовкам list/table (только заполненные характеристики и название; полный дизайн ещё впереди). В карточках категории/бренда/бейджа и странице категории добавлены вызовы общего макета для будущих данных.

**Что ещё не готово:** генерация ввода и сохранение значений в форме товара/категории; отдельное хранилище значений категорий; две границы диапазона; фильтр и движок вариантов. Категорийные поля поэтому пока имеют настройки и точку вывода, но не загружают значения из product_id. Существующие записи/значения пользователя не создавались и не перезаписывались для демонстрации. Поля появляются на сайте только когда сохранены реальные значения.

## 16. Значение чекбокса по умолчанию (C58)

У одиночного флажка (`checkbox_mode=single`) виден селект `checkbox_default` с вариантами не заполнено/Нет/Да. При `options` вместо него виден текстовый `checkbox_default_option`: точное название одного варианта из таблицы, например «8 гб». Пусто означает отсутствие значения по умолчанию. Оба условия showon нативные, внутри params: `.type:checkbox[AND]checkbox_mode:single/options`.

`CheckboxType` нормализует режим, булев default и текст (до 255 символов). `FieldModel` до записи проверяет непустой default по названиям опций этого поля; отсутствующий или неоднозначный вариант отвергается с понятным сообщением. В конфигурации сохраняется `checkbox_default_option_id` со стабильным ID опции, а текст используется для редактирования. Подставленный клиентом ID не принимается. Для новой опции ID записывается в той же транзакции связей после insert; компенсация определения при сбое сохранена. `getItem` подставляет актуальное название по ID, а переименование выбранной опции при том же сохранении сохраняет привязку. Для удаления такой опции нужно очистить или сменить default.

Схема БД не меняется: defaults — настройки определения, не значения товаров. C59 применяет default к новым формам товара/категории; сохранённые записи и явно очищенные поля не заполняются автоматически.

## 17. Ввод значений в товаре и категории (C59)

Поля включены в существующие вкладки после «Основное»: общая «Поля» или отдельные вкладки групп по `tab_mode`. Поля без группы находятся в общей вкладке. Пустые опубликованные группы сохраняют прежнее сообщение. Бренды и бейджи не получают поля категории.

- `Administrator\Fields\ValueTypeInterface` расширяет контракт определения методами `input/defaultValue/decode/encode`. `input` возвращает нативный XML, `encode` — простые строки и/или отдельный текст. Провайдер не выполняет SQL. Basic использует `Type\NativeValue`; каждый из шести классов может переопределить методы при дальнейшем уточнении типа.
- `Administrator\Fields\FieldValues` выбирает опубликованные доступные определения и группы, учитывает включённые провайдеры, добавляет XML в Form, загружает значения и записывает их. Для товара охват — основная/дополнительные категории и их предки; для категории — сама запись. Новая категория сначала получает общие поля, после первого сохранения доступны назначения по её ID.
- Имена POST: `jform[custom_fields][f_<id>]`; скрытый `custom_fields_present[f_<id>]` отличает снятые чекбоксы от поля, которого не было в форме. Не показанные, недоступные или переставшие применяться значения сохраняются. При смене категорий товара набор полей обновляется после сохранения/повторного открытия; собственного AJAX/JS нет. Новые применимые поля, которых не было в POST, не записываются и не блокируют первое сохранение.
- Single checkbox — не заполнено/Нет/Да; набор — нативные `checkboxes` со стабильными ID опций; list — поиск Joomla и настройка мультивыбора; text — длина/подсказка; editor — штатный редактор; number — нативный number; range — одноразовый subform с полями «От/До» и настраиваемыми подписями. Изображения опций относятся к выводу значений на витрине; в редакторе выбор по названию.
- Проверка до `Table::store`: обязательность (0 допустим), собственные ID опций, длина текста, очистка HTML, пределы/точность/шаг числа, обе границы диапазона и `from <= to`. DECIMAL записывается из нормализованной строки без преобразования обратно из float. Проверка шага/предела использует числовое сравнение. Настройки типов продолжим уточнять отдельно.
- Только новые формы получают `text_default` и default чекбокса, включая стабильный ID из C58. Ошибочный POST и очищенные значения не заменяются default. Обязательное поле проверяется при отправке его значения/маркера.

### Хранение и обновление

У товаров: `field_values` (`option_id/num/str`, теперь также `num_end`) и `field_texts`; редактирование базового товара затрагивает только `variant_id IS NULL`. Галерея `field_media.field_id=0` и значения вариантов не меняются. У категорий: отдельные `category_field_values` с `category_id,field_id,option_id,num,num_end,str` и `category_field_texts` с `category_id,field_id,value`. Значения характеристики не хранятся в JSON. Тип `files` использует media-строки и отдельную `category_field_media`; контракт и настройки — [FILES_FIELD.md](FILES_FIELD.md).

`script.php::upgradeFieldValueStorage()` аддитивно добавляет nullable `num_end` и индекс существующей таблице, создаёт две таблицы категорий. Новая установка использует install SQL; uninstall SQL перечисляет новые таблицы. Версия 0.1.0. Не деинсталлировать пакет ради миграции.

Подготовленные значения записываются в транзакции связей после завершения Joomla `Table::store`, заменяются только конкретные показанные поля. При удалении записи чистятся её простые/текстовые значения; защита удаления определения/используемых опций учитывает обе сущности. Ошибка проверки не пишет карточку. При техническом сбое транзакции значений категория уже могла быть сохранена Joomla; транзакция значений откатывается, модель сообщает ошибку. Общая атомарность карточки/всех связей — прежнее ограничение Joomla LOCK TABLES.

### Витрина

`Site\Support\EntityFields` пакетно загружает значения продуктов и категорий; `ProductFields` сохраняет совместимый вход. Для категорий подключены card/page в `CategoriesModel`, только `Taxonomy::category()`. Диапазон выводится как «от – до» с единицей. Существующие `load_*`, `in_*`, `format_*` применяются общими макетами `fields/default.php` и `value.php` (`dl/dt/dd`). Значения появляются после сохранения пользователем; демонстрационные записи не создаются.

Автоматические сценарии ввода/сохранения и браузерные проверки не запускались. Следующий шаг — уточнение поведения типов на реальных формах пользователем; фильтр и варианты остаются отдельными этапами.

## 20. Дополнительная галерея изображений (2026-10-09)

Отображение фото: `gallery_fit=cover` по умолчанию заполняет рамку с обрезкой краёв без искажения; `contain` вписывает целиком с полями, `original` сохраняет пропорции подготовленной копии, не увеличивает её и убирает фиксированную высоту. `gallery_ratio=1x1/4x3/16x9` задаёт формат рамки первых двух режимов (по умолчанию 4x3). Оба макета используют общую карточку с классами Bootstrap; исходники, WebP и контексты ресайза не меняются. У original высота карточек может различаться.

Basic provider регистрирует тип `gallery` для товаров и категорий. Он повторно использует изолированный экземпляр `GalleryField` и drag/drop код, но загружает изображения отдельным маршрутом, который сверяет тип, состояние, уровень доступа и группу поля. Галерея товара использует `field_media` с положительным `field_id`, основная галерея товара остаётся с `field_id=0`; файлы остаются в отдельном обработчике и различаются непустым MIME. Схема не менялась.

Настройки определения: максимум 1–100 изображений (50 по умолчанию), галерея/слайдер Swiper, 1–6 колонок отдельно для xs/sm/md/lg/xl/xxl Bootstrap (0/576/768/992/1200/1400 px), Fancybox, подписи и подпапка хранения. В слайдере колонки задают число видимых изображений. Старое `gallery_columns` используется для xl/xxl, прежний list преобразуется в галерею с одной колонкой на каждом размере экрана; форма показывает эффективные настройки без массового пересохранения. Физический адрес — `<общая папка изображений>/field-galleries/<field id>/<подпапка>/<год>`; имя папки очищается до безопасного ASCII. Обработка выполняется общим `ImageUploader` (общие ограничения и WebP), на витрине используются контексты общего плагина ресайза. Контракт переопределяемого макета описан в `LAYOUTS.md`.

## 18. Ограничения в редакторе (C60)

Подпись настройки единицы измерения у number/range использует общий переведённый ключ `COM_DHARMASHOP_FIELD_UNIT_LABEL` («Единица измерения»); исправлено 2026-10-08 вместо отсутствующего `COM_DHARMASHOP_ORDER_UNIT_LABEL`.

Basic `NativeValue::input()` добавляет нативные `description` с `translateDescription=false`. Под полями видны обязательность, максимальная длина text, минимум/максимум number/range (если заданы), действующий шаг с точкой отсчёта, допустимая точность и единица измерения. Выбор списка поясняет одиночный/множественный режим. Для range ограничения числа стоят у обеих границ, общее пояснение — обе границы заполнены вместе и начало не выше конца. Это те же settings, которые применяет encode; дополнительной копии конфигурации, JS/CSS и изменения схемы нет. Тексты help-блока экранируются.

Валидация теперь возвращает конкретное сообщение вместо общего: обязательность, длина с пределом, число/точность, минимум/максимум, шаг с базой, одна отсутствующая граница или обратный диапазон. Компонент сохраняет обёртку с названием поля. Предел хранилища чисел (12 целых/6 дробных цифр) также указан. Поведение сохранения и значения не меняются, пользовательские карточки не пересохраняются.

## 19. Editor исключён из тизера (C61, 2026-10-08)

Для типа `editor` блок списка показывает заблокированные переключатели «Загружать поле / Выводить поле» со значением Нет и недоступный формат. Нативные XML showon переключают обычные элементы и отключённые представления при выборе типа новой записи; служебные элементы имеют filter=unset. Сохранённый тип по-прежнему менять нельзя.

`DisplaySettings::normalize()` принудительно задаёт `load_card=0`, `format_card=comma`, `FieldTable::check()` — `in_card=0`, независимо от POST. `FieldModel::getItem()` отдаёт эффективные нули и для старых определений. `EntityFields` исключает editor из запроса определений в контексте card — длинный текст не загружается даже при старых флагах в БД. Это действует для товарных и категорийных полей и всех списков, использующих общий загрузчик. Полная страница и её load_page/in_page/format_page сохраняют прежнее поведение. Массового пересохранения определений/пользовательских значений нет; старые флаги приводятся к нулям при следующем сохранении определения. Схема не менялась.

## 20. Text/editor без фильтра (C62, 2026-10-08)

Для text/editor блок «Фильтр» показывает отключённое Нет с пояснением. Нативный showon скрывает обычный переключатель и показывает служебный `filterable_text_disabled` (disabled, filter=unset) при выборе типа; экран уже выводит весь display_filter fieldset. У прочих типов обычная настройка сохранена.

`FieldModel::getItem()` отдаёт эффективный filterable=0 для старых text/editor. `FieldTable::check()` принудительно сохраняет filterable=0 независимо от POST. Значения полей и остальные настройки не меняются, миграции и массового пересохранения нет. Движок фильтра всё ещё отдельный этап: при его реализации исключать text/editor из выборки даже при старом filterable=1 в БД.

### Группы на полной странице товара (2026-10-08)

Под верхними колонками карточки — вкладка полного описания и отдельные вкладки групп заполненных видимых полей. Учитываются прежние load_page/in_page, публикация группы/поля, доступ поля и применимость к товару. Порядок группы/поля сохраняется. Поля без группы — «Характеристики», пустые вкладки не выводятся. Административный tab_mode регулирует редактор и не ограничивает эти вкладки витрины. Значения по-прежнему рисует fields/default → fields/value. EntityFields передаёт group_id/group_title без новых SQL; подробности — LAYOUTS.md.

### Выбор полей для интро товара (2026-10-08)

В «Отображение → Полная страница» добавлен нативный переключатель «Выводить в интро товара» с пояснением места: рядом с кратким описанием возле галереи, отдельно от карточек каталога и вкладок групп ниже. `params.show_intro` нормализуется компонентом в 0/1; при отсутствии — 0. Старые определения не пересохраняются массово, поэтому все по умолчанию выключены. Настройка видна для target=product при load_page=1; EntityFields проверяет назначение/контекст. Флаг независим от in_page, общий формат format_page, прежние доступ/публикация/применимость сохраняются. Отдельный default_intro.php — в LAYOUTS.md.

Уточнение редактора (2026-10-08): блоки card/page в admin/tmpl/field/edit.php используют явные renderField, а не целый fieldset. Для новых настроек кроме XML требуется добавление вызова туда; show_intro выведен после in_page. Серверный HTML новой формы проверен по HTTP: переключатель присутствует, default=0 и showon указывают на jform[target]/jform[params][load_page].

## 21. Файлы (2026-10-08)

Тип `files` (store=`media`) в базовом провайдере, независимые экземпляры общего загрузчика для товара/категории, лимиты и подписи. Основная галерея `field_id=0` сохраняется. Подробнее: [FILES_FIELD.md](FILES_FIELD.md).
