# Оплата: раздел, типы-плагины и подключение платёжных шлюзов (C83)

Дата: 2026-10-09. По запросу пользователя: «Оплата» — отдельная сущность с тем же принципом, что «Доставка» (C80): общий раздел, расширяется плагинами-типами; первый тип — «Стандартная оплата» (оплата вне сайта, без страницы оплаты), второй — «Тестовая оплата» (песочница, имитация шлюза для проверки всего процесса); в доставке — правило, какая оплата доступна для способа доставки.

## 1. Что где лежит

| Что | Где |
|---|---|
| Таблица способов | `#__dharmashop_payment_methods`: `title`, `alias`, `plugin` (id типа = element плагина группы `dharmashoppayment`), `description`, `image`, `params` (JSON настроек типа), `paid_status_id` (статус заказа после подтверждённой оплаты, NULL — не менять), `is_default`, `state`, `access`, `ordering` |
| Платежи | `#__dharmashop_payments`: одна запись на попытку оплаты заказа (`state` pending/paid/failed/cancelled, `external_id` шлюза — уникален вместе с `method_id`, защита от повторных вызовов) |
| Заказ | `orders.payment_method_id`, `payment_title`, `payment_data` (снимок: type, title, rows, data), `payment_status` (`none` — оплата вне сайта, `pending`, `paid`, `failed`, `cancelled`), `paid` (время оплаты) |
| Контракт, реестр, службы | `com_dharmashop/admin/src/Payment/`: `TypeInterface`, `TypeRegistry`, `Method`, `Context`, `Selection`, `Initiation`, `Outcome`, `OrderPayment`, `Urls`, `PaymentInputException`, `PaymentService` |
| Раздел админки | виды `payments`/`payment`, модели, `PaymentController`/`PaymentsController`, `forms/payment.xml`, `forms/filter_payments.xml`; право `dharmashop.payment.manage`; пункт меню «Оплата» (плагин `plg_system_dharmashopmenu`) |
| Оформление | `site/tmpl/checkout/default_payment.php` (плитки-вкладки, как у доставки) и `default_payment_tile.php`; боковая панель — блок «Способ оплаты» |
| Страница оплаты и обратные вызовы | вид `payment` (`site/src/View/Payment`), контроллер `PaymentController` (`callback`, `ajax`); страница заказа показывает оплату и кнопку «Оплатить» |
| Плагины | `plg_dharmashoppayment_standard`, `plg_dharmashoppayment_sandbox` (в общем пакете, включаются при установке) |
| Правило «какая оплата для какой доставки» | `shipping_methods.payment_ids` («1,3», пусто — любая); поле в боковой колонке формы способа доставки |

## 2. Поведение

- Если способов оплаты нет, шага оплаты нет (оформление как раньше). Если есть — выбор обязателен; **сервер** проверяет, что способ опубликован, доступен для суммы заказа (с доставкой), разрешён для выбранной доставки, и данные типа корректны (`PaymentInputException`).
- На странице оформления способы оплаты — плитки-вкладки в ряд под доставкой. Недоступная для выбранной доставки оплата скрывается без перезагрузки (карта «доставка → разрешённая оплата», `data-payment-map`); отключённая радиокнопка в запрос не уходит.
- После создания заказа `PaymentService::initiate()` спрашивает тип: **`Initiation::none()`** — оплата вне сайта (покупатель видит инструкцию в заказе и письме, статус оплаты `none`); **`Initiation::page()`** — переход на страницу оплаты сайта (`view=payment`, макет типа `renderPayment`); **`Initiation::redirect($url)`** — переход на внешний шлюз.
- Ответы шлюза приходят на `index.php?option=com_dharmashop&task=payment.callback&method=<id>&order=<id>&action=<действие>` (GET или POST, без токена формы Joomla). **Подлинность проверяет тип** (подпись, секрет шлюза, повторный запрос к API); ядро проверяет только, что заказ оплачивается именно этим способом. Действие `notify` — уведомление сервера (ответ — текст и код), остальные — возврат покупателя (редирект на страницу заказа с сообщением).
- Итог (`Outcome`: paid / pending / failed / cancelled) применяет `PaymentService::apply()`: статус оплаты заказа, запись в `payments`, при `paid` — смена статуса заказа на «после оплаты» способа (`OrderStatusService`, письмо покупателю по статусу) и событие `onDharmaShopPaymentStatusChanged`. Оплаченный заказ не откатывается повторными вызовами.
- Цены способа оплаты (наценка, скидка за предоплату) в ядре нет — позже, по событию/расширению `Context`.

## 3. Контракт типа (`TypeInterface`)

`id`, `label`, `description`, `settingsPath` (Form XML: `<fields name="params"><fields name="<id>"><fieldset name="type_<id>">`, поля с `showon=".plugin:<id>"`), `normalizeSettings`, `available(Method, Context)`, `describe(Method, Context)` (строки «подпись — значение» для оформления, боковой панели, заказа, писем), `validateInput` (данные покупателя: `payment[<id>][<ключ>]`), `ajax`, `render($displayData)` (панель на оформлении), **`initiate(Method, OrderPayment, Urls): Initiation`**, **`renderPayment($displayData)`** (страница оплаты сайта), **`handle(Method, OrderPayment, $action, $input): Outcome`** (обратный вызов).

`Urls`: `pay()`, `order()`, `callback($action, $extra)` — абсолютные адреса для шлюза. `OrderPayment`: `id`, `number`, `key` (секрет заказа — им можно подписывать запросы), `total`, `currency`, `status`, контакты, `data` (снимок).

Регистрация: плагин группы `dharmashoppayment` на событие `onDharmaShopPaymentTypesCollect` вызывает `$registry->register(new …Type())` (как у доставки).

## 4. Правила макета типа

- Любой вывод — через макет плагина (`PluginHelper::getLayoutPath('dharmashoppayment', '<id>', 'default'|'payment')`), чтобы его можно было переопределить: `templates/<шаблон>/html/plg_dharmashoppayment_<id>/default.php`.
- Макет `default.php` выводит **только панель** выбранного способа: корень `<div data-payment-option data-method-id="<id>">` (у невыбранных скрыт `d-none`), внутри описание, сведения, поля `payment[<id>][<ключ>]` с `data-summary-label`. Плитку с радиокнопкой `payment_method` рисует страница оформления.
- Только классы Bootstrap 5, без своего CSS/inline-стилей; значения в вывод — через `htmlspecialchars`.
- Изображение способа: контекст `payment.option` (96 × 96, `docs/IMAGE_RESIZE.md`), `ImageUrl::resolve()`.

## 5. Безопасность

- Сумму и доступность определяет сервер из заказа; из браузера принимается только id способа и данные типа.
- Подпись обратного вызова — на типе; сравнение — `hash_equals`; неизвестное действие/подпись — `Outcome::ignored()` (400, статус не меняется). Тип не должен доверять `amount` из запроса, а сверять с `OrderPayment::total`.
- Ошибки типов не раскрываются покупателю, пишутся в журнал Joomla (`com_dharmashop`) без реквизитов.
- Доступ к странице оплаты — как к заказу: владелец, гость этого сеанса или секретный ключ (`key`) из ссылки.

## 6. Первые типы

- **Стандартная оплата (`standard`)** — оплата вне сайта: инструкция покупателю (настраивается; попадает в заказ и письмо), пределы суммы заказа. Способов можно завести несколько («Наличными при получении», «Картой курьеру»).
- **Тестовая оплата (`sandbox`)** — образец шлюза и средство проверки процесса: после заказа открывается страница оплаты с кнопками «успех», «отказ», «отмена»; ссылки подписаны HMAC секретом заказа (`sign()`), обработка — `handle()` (`result` и `notify`). Деньги не списываются. Для проверки письма об оплате задайте у способа «Статус заказа после оплаты».

## 7. Как подключить настоящий шлюз

1. Плагин группы `dharmashoppayment` с `Type`, реализующим `TypeInterface`; в `settingsPath` — ключи магазина (shop id, секрет) в настройках способа (в репозиторий секреты не попадают).
2. `initiate()`: создать платёж на стороне шлюза (REST), сохранить его id в `Initiation::redirect($url, ['external_id' => …])` или вернуть `Initiation::page()` и показать кнопку в `renderPayment()`.
3. `handle()`: для `notify` проверить подпись/запросить статус платежа у шлюза по API; `Outcome::paid($ref, $amount)` — только если сумма и валюта совпадают с заказом; ответ серверу шлюза — `body`.
4. Для `return` (покупатель вернулся) — `Outcome::pending()` или результат, если шлюз его сообщил; страница заказа покажет статус.
5. Тестировать сначала на песочнице шлюза; поведение процесса отлаживается на типе «Тестовая оплата».

## 8. Идеи (не сделано)

- Наценка/скидка способа оплаты (строки итога заказа через `order_adjustments`).
- Кнопка «Отметить оплаченным» в карточке заказа админки, возвраты (`refunded`).
- Фискализация и чеки, повторная оплата по ссылке в письме, срок жизни неоплаченного заказа.
- Телеграм-уведомление о платеже (общий план уведомлений).
