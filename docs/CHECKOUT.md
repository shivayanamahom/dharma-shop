# Оформление заказа — план реализации

Дата: 2026-10-08. C70: пользователь согласовал конструктор в компоненте. C71: контактные поля/согласия выводятся на странице checkout отдельными макетами, справа состав текущей корзины. Административные определения и вывод установлены на test.test. Доставка/оплата, серверная проверка данных посетителя и создание заказа ещё не подключены.

## 1. Состав страницы

1. Контактные данные получателя.
2. Способ доставки и его дополнительные поля.
3. Способ оплаты и его дополнительные поля.
4. Согласия.
5. Итоги и отправка заказа.

Контактные данные получателя сохраняются снимком в заказе. Они не должны автоматически заменять профиль покупателя: получатель может быть другим человеком. Окончательная схема привязки стандартных полей к contact_name/contact_email/contact_phone будет закреплена при реализации.

## 2. Конструктор в настройках

Принят встроенный конструктор на нативных Joomla subform. Дополнительные интеграции смогут расширять форму через зарегистрированные события. Имена событий пока не назначены.

Вкладка «Оформление заказа» уже существует. Первые группы:

### Контактные данные получателя

Повторяемые строки, порядок меняется штатным subform. Минимальные настройки поля:

- Включено.
- Тип: строка, телефон, email, многострочный текст.
- Стабильное техническое имя (уникальное внутри формы).
- Название.
- Подсказка в поле.
- Обязательное.

Конструктор изначально пустой, записи добавляет пользователь; автоматически сохранять за него имя, телефон, email и комментарий не стали. Техническое имя не должно меняться при переименовании подписи. Проверка email/телефона, длины и обязательности будущих значений — при подключении формы; конкретные ограничения и телефонная маска — при обработке типов, без навязывания одного формата всем странам.

### Согласия

Повторяемые строки со стабильным кодом, включением, текстом флажка, необязательной ссылкой на документ/подписью ссылки и признаком обязательности. По умолчанию новая строка включена и обязательна; это определение будущего флажка, не факт согласия посетителя. При подключении формы флажки на сайте будут изначально сняты, обязательность проверит сервер. При записи заказа будут сохраняться факт согласия, код, текст/ссылка документа на момент заказа и время, чтобы изменение настроек не меняло историю. Хранилище согласий определить при реализации заказов, сейчас схему не менять.

Существующие параметры order_qty_*, единицы и складские флаги сохраняют имена и значения. Их группа ниже конструктора должна называться понятно — «Правила заказа товаров». Никакого массового пересохранения параметров.

## 3. Доставка и оплата

Предложенная пользователем модель совпадает с подготовленной схемой (§5.10 ARCHITECTURE.md): отдельные пункты меню магазина «Доставка» и «Оплата», в каждом CRUD способов с выбором установленного плагина и его настройками.

- Доставка: группа плагинов dharmashopshipping, первые отдельные реализации — доставка и самовывоз.
- Оплата: группа dharmashoppayment, первая реализация — оплата при получении; онлайн-интеграции отдельными плагинами.
- Одна запись способа ссылается на плагин; один плагин может обслуживать несколько записей, например несколько пунктов самовывоза.
- Компонент отвечает за список доступных способов, выбор, общий пересчёт и снимок в заказе. Плагин — за собственные настройки, поля, доступность, расчёт/проверку и интеграцию.
- Идентификаторы выбранных способов и суммы проверяет сервер. Суммы из браузера не принимаются как источник итогов.

## 5. Реализованные определения (C70)

`admin/config.xml`, вкладка order: группы checkout_contacts / checkout_agreements / order_product_rules. Параметры checkout_fields и checkout_consents сохраняются штатным com_config в params компонента; прежние order_qty_*, order_unit и складские настройки сохраняют имена/значения. Новые XML: forms/checkout_contact.xml и checkout_consent.xml. Каждый список ограничен 50 строками, порядок — из subform, исходно оба пусты.

Строка контакта: type (text/tel/email/textarea), name, label, hint, required (0), enabled (1). Строка согласия: name, text, url, link_label, required (1), enabled (1). Техническое имя можно оставить пустым: при сохранении оно создаётся из названия поля или текста согласия штатной транслитерацией Joomla, с подчёркиваниями. При совпадении добавляется `_2`, `_3` и далее; заданные вручную имена резервируются до генерации. Итоговое имя — 1–64 символа `[a-z][a-z0-9_]*`, уникально внутри списка; изменение подписи не меняет сохранённое имя. Название/подсказка/подпись ссылки до 150 символов, текст согласия до 2000, URL до 2048. HTML не сохраняется в текстах. URL — нативная проверка Joomla, HTTP/HTTPS либо относительный адрес; поле link_label показывается штатным showon при непустом URL.

CheckoutdefinitionsField наследует штатный SubformField: сначала нативная фильтрация строк, затем заполнение пустых технических имён до проверки com_config. CheckoutdefinitionsRule расширяет SubformRule: сначала нативная проверка обязательности/типов/regex/URL, затем уникальность имён, пределы длины и непустой текст/название. При проверке данные Registry/stdClass приводятся к массивам: Form::validate() Joomla преобразует в объекты даже корректно заполненные строки. Ошибки выбрасываются как исключения, чтобы дополнительная штатная проверка subform не перезаписала их результат. Собственного административного JS/CSS нет. Новые определения не мигрировались в БД и за пользователя не сохранялись. PHP syntax проверен; сценарии сохранения в браузере не запускались. Следующий шаг — генерация формы checkout по этим определениям и проверка данных посетителя.

У контакта типа tel добавлена настройка `mask`, видимая через штатный showon только для телефона. По умолчанию `+7 (###) ###-##-##`; `#` обозначает вводимую цифру, остальные символы — фиксированное оформление. Можно задать свою маску (до 64 символов, хотя бы один `#`); пустая при сохранении заменяется стандартной. C71 подключил маску при вводе посетителя; серверная проверка номера остаётся этапом создания заказа.

## 6. Вывод формы (C71)

У каждого контакта настройка `show_label` (по умолчанию 1). При Нет заголовок визуально скрыт (`visually-hidden` сохраняет доступную подпись), в input/textarea остаётся плейсхолдер из hint; если он пустой — название поля. Для обязательного поля к плейсхолдеру добавляется `*`. Устаревшие определения без show_label показывают заголовок. Маска телефона не дублируется под полем — применяется только внутри input.

По запросу пользователя основной макет подключает отдельные части: `default.php` → `default_form.php` → contacts / agreements / summary. Контактные text/tel/email — две колонки от md, textarea — во всю ширину. Порядок, включение, подписи/подсказки, обязательность читаются из C70; значения пустые, профиль покупателя не подставляется автоматически. HTML экранируется. Имена будущего POST: `recipient[<name>]`, `consents[<name>]`. Нативные type=email/required/maxlength; текущие пределы ввода text 150, tel 64, email 254, textarea 2000 символов. Это ограничения интерфейса, серверная проверка данных посетителя ещё впереди.

`checkout.js` (ассет com_dharmashop.checkout, только на checkout) применяет маску tel из настроек: `#` — цифровое место; ввод/вставка/автозаполнение форматируются, Backspace/Delete проходят разделители, неполный введённый номер помечается через setCustomValidity. JavaScript не отправляет данные. В первоначальном C71 отправка была заблокирована; C73 подключил кнопку и обработчик (ниже). Согласия сняты, required задан из определения; ссылки HTTP(S)/относительные, отдельно, без HTML в тексте.

Правая карточка показывает реальные позиции корзины (количество × цена, варианты, ошибки), скидку, корректировки и сумму. Данные из CartSession::current / CartService::lines / totals; просмотр не создаёт гостевую корзину, итог не берётся из браузера. Замена нулевой цены сохраняется. Пустая корзина — сообщение и ссылка обратно. Доставка/оплата будут вставлены между контактами и согласиями отдельными макетами, без пустых способов и фиктивного расчёта сейчас. CSS нет, только Bootstrap. PHP/JS syntax проверен; пользовательские настройки/корзина не менялись, отправка заказа не запускалась.

## 8. Подтверждение и состав заказа (C75, 2026-10-08)

`checkoutcomplete` показывает доступный сохранённый заказ: компактный заголовок с галочкой, дата, статус, сумма, действия «Перейти к заказу» / «Продолжить покупки». Основное действие открывает вид `order`. Без действующего подтверждения остаётся нейтральное сообщение.

`OrderAccess::remember` выдаёт гостевой доступ только после успешного создания/повтора собственного заказа. `Site\Model\OrderModel` дополнительно ограничивает запрос владельцем до загрузки состава и контактов. В URL нет секретов. Гостю просмотр доступен в той же сессии браузера. Подробности — ORDERS.md, C75.

## 9. Предзаполнение для вошедшего пользователя (2026-10-08)

Если посетитель вошёл, форма контактов подставляет всё, что о нём известно (`Site\Support\CheckoutPrefill`, только данные самого пользователя). Источники по приоритету: снимок контактов его последнего заказа (значения всех полей конструктора, в том числе произвольных: организация и т. п.; сопоставление по техническому имени и типу поля), запись покупателя с его `user_id` (телефон), учётная запись Joomla (имя, e-mail) и телефон профиля (`profile.phone`). Поля, введённые при ошибке, не перезаписываются (значения в сессии важнее); гостю ничего не подставляется. Поле конструктора без источника остаётся пустым.

## 10. Недоступные позиции (2026-10-08)

Позиция может стать недоступной после добавления в корзину: товар сняли с публикации или скрыли его категорию, закончился или стал меньше остаток (учёт остатков), убрали цену, изменились правила количества (минимум, шаг, максимум), плагин вернул ошибку. Такая позиция не входит в сумму и блокирует «Оформить заказ» (сервер проверяет это и при создании заказа). Над составом (на странице корзины и в сводке оформления) выводится предупреждение со списком причин и кнопками «Удалить недоступные» и, если позиция не хватает остатка, «Уменьшить до наличия» (до наибольшего допустимого количества: минимум плюс целое число шагов; позиции, которые уменьшить нельзя, удаляются). Действие — POST `cart.removeUnavailable` (`mode=remove|reduce`, токен; `return=checkout` возвращает на оформление, остальное — на корзину). Макет предупреждения — `layouts/components/dharmashop/cart/unavailable.php` (переопределяется); на оформлении кнопки используют отдельную форму `dharma-cart-fix` (атрибут `form`), потому что сводка лежит внутри формы заказа.
