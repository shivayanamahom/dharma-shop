# Разработка: стенд, сборка, проверки

## Общие поля группы: проверки (2026-10-11)

```sh
set -a
. dev/.env
set +a
php dev/check-group-common-fields.php
php dev/check-group-common-scope.php
# Только если нужна новая опубликованная демогруппа:
php dev/check-group-common-fields.php --demo
php dev/bench/group-fields-scale.php
# HTTP запускать после масштабного замера, без его параллельных вставок:
python3 dev/bench/group-http.py
```

Без --demo собственные группы/товары переводятся в корзину, manifest существующего demo не заменяется. Scope-тест оставляет свои категории/поле в корзине. ID категории 51, полей/опций и ссылки на имеющиеся медиа — fixtures test.test, не данные других магазинов. --demo оставляет группу и шесть товаров опубликованными; manifest — ignored dist/common-fields-demo.json.

Масштабный тест берёт первый товар manifest, создаёт изолированные таблицы со случайным префиксом cgqa_, проверяет реальные EntityFields/CategoryModel на 100 и 100000 товарах. EXPLAIN требует индекс владельца. В finally удаляются только собственные таблицы; магазин и чужие bn_* не меняются. Это загрузка полей/списка без активных фильтров; групповые фасеты и конкурентная HTTP-нагрузка не измеряются.

HTTP делает 20 замеров после прогрева для каждого макета/AJAX/страницы, проверяет отсутствие group_field_* SQL в Joomla debugbar, не экспортирует debug/session данные. JSON-метрики — dist, итог — QA_GROUP_COMMON_FIELDS.md. Для адресного развёртывания вызвать GroupStorage::upgradeGenerator(); установщик вызывает upgrade автоматически. Новых CSS/JS нет.

## Скрипты `dev/`

| Скрипт | Что делает |
|---|---|
| `boot.php` | поднимает консольное приложение Joomla на `DHARMA_SITE` |
| `install.php <zip>` | устанавливает пакет как «Установка расширений»; передавайте абсолютный путь к zip |
| `uninstall.php` | удаляет пакет `pkg_dharmashop` (вместе с таблицами) |
| `sync.sh` | раскладывает исходники в сайт без сборки zip (после первой установки): компонент, общие макеты, модули корзины, поиска, фильтра, категорий и товаров (код, media, языки) |

| `install-module.php <папка> [позиция]` | устанавливает модуль из папки репозитория штатным установщиком (создаёт запись расширения и, если указана позиция, опубликованный экземпляр) |
| `reindex-search.php` | полная пересборка поискового индекса на тестовом сайте |
| `db.sh "SQL"` | запрос к базе сайта; `PFX_` заменяется префиксом таблиц |

| `save-category.sh <extension> "Название" [родитель] [цвет]` | создаёт категорию/бренд/бейдж через форму админки по HTTP |
| `save-product.sh "Название" <catid> <артикул> <цена> [brand] [badge]` | создаёт товар через форму админки по HTTP (нужен вход `web-login.sh`) |
| `security-upload.sh` | проверка защиты загрузчика изображений (токен, права, подмена типа, обход путей, SVG); см. `docs/SECURITY.md` |
| `bench/bench.php` | генератор тестового каталога и замеры (`generate`/`run`/`all`/`drop`), см. `docs/BENCHMARKS_NOTES.md` |
| `bench/report.php` | собирает `docs/BENCHMARKS.md` из `dev/bench/results/*.json` |
| `scenario/fixture.py [фаза …]` | наполняет **чистую** локальную установку мини-магазином через формы админки по HTTP: склады, поля, категории, 8 товаров, 2 группы с вариантами, доставка, оплата, акции, контакты оформления, посадочные страницы, модули. Повторный запуск пропускает уже созданное |
| `scenario/scenarios.py [раздел …]` | сценарии посетителя и сотрудника на наполненной установке (каталог, фильтры, поиск, страницы товаров и JSON-LD, избранное, корзина, купоны, оформление, лимиты, посадочные, админка и справка, права оператора, «Мои заказы», скорость); разделы: `browse product favorites cart checkout landing admin users perf all`; печатает PASS/FAIL, находки и предупреждения PHP из ответов |

Адреса покупателей уникальны для каждого запуска; лимит заказов с одного IP на время сценариев поднимается через форму настроек и возвращается к 10.


## Адресное обновление переводов

Joomla загружает установленные переводы компонента из `administrator/language/<язык>/com_dharmashop.ini` и `language/<язык>/com_dharmashop.ini`. При адресной синхронизации языки нужно копировать туда из admin/site language исходников; копии внутри components/com_dharmashop/language не заменяют установленные. Проверять актуальность обоих RU/EN файлов. При установке пакета это делает манифест `<languages>`. Для кнопок админки используйте классы из установленного joomla-fontawesome.css: например, icon-folder-open; icon-layer-group в Joomla 6.1.4 отсутствует.

## Сборка и установка

`build.sh` перед упаковкой сверяет COM_DHARMASHOP-ключи в Form XML и XML типов пунктов меню с RU/EN словарями администратора. Если перевод пропущен или имя ключа расходится, сборка останавливается с указанием языка, ключа и файла.

```bash
./build.sh                                   # dist/pkg_dharmashop-<версия>.zip
DHARMA_SITE=/Volumes/Work/Server/www/test php dev/install.php "$PWD/dist/pkg_dharmashop-0.1.14.zip"
```

Версии манифестов меняются только при выпуске пакета через `python3 dev/release.py bump <версия> --since <последний-тег>`; во время разработки сохраняется версия последнего выпуска. Новые расширения добавляйте в `EXTENSIONS` в `build.sh` и в `<files>` манифеста `pkg_dharmashop.xml`.

В манифестах модулей используйте читаемое значение в `<name>`, а не языковой ключ: штатный журнал действий Joomla сохраняет это поле буквально и не переводит его. Ключи `<description>` по-прежнему переводятся через `*.sys.ini`.

С C32 пакет содержит файловое расширение `files_dharmashop_layouts` (первым), компонент и два SEO-плагина. Оно устанавливает карточки из `files_dharmashop_layouts/layouts/` в общую библиотеку `layouts/components/dharmashop/`. Только файлы, перечисленные в манифесте, принадлежат расширению; дополнительные пользовательские файлы не перечисляются.

Первый переход со старой папки компонента выполняется **обновлением пакета**, без деинсталляции: пакетный скрипт сохраняет её перед удалением Joomla и переносит в новую папку. При ошибке или конфликте остаётся каталог восстановления `tmp_path/dharmashop-layouts-*`, указанный в сообщении. Не удаляйте его до разбора результата. Схема БД не меняется, каталог магазина сохраняется.

После установки этого обновления `dev/sync.sh` копирует общие макеты без `--delete`, сохраняя дополнительные файлы; старый `/layouts/` компонента исключён из удаления rsync до штатной миграции. Сам sync не регистрирует файловое расширение и не выполняет миграцию, поэтому для первого перехода не подходит. Изменения поставляемых файлов при последующих обновлениях держите в переопределениях шаблона.

- После изменения схемы: удалить пакет (`dev/uninstall.php`), собрать, установить, проверить число таблиц (`dev/db.sh "show tables like 'PFX_dharmashop%'"`). Пока релизов нет, схему правим прямо в `install.mysql.utf8.sql`; после первого релиза — только через `sql/updates/mysql/<версия>.sql`.

Не деинсталлировать пакет ради этого изменения; текущие данные сохраняются. Новая установка использует обновлённый `install.mysql.utf8.sql`. Версия остаётся `0.1.0`.
- C51: `script.php::upgradeFieldGroupTabs()` так же аддитивно добавляет `fieldgroups.tab_mode` со значением `fields`. Не деинсталлировать пакет; прежние группы и значения сохраняются. Административная папка `layouts` явно включена в манифест компонента.
- C59: `script.php::upgradeFieldValueStorage()` добавляет `field_values.num_end` и индекс, создаёт `category_field_values/category_field_texts`. Установка только обновлением; определения, опции, значения и пользовательские записи сохраняются. Автоматические сценарии без запроса пользователя не запускать.
- Изменения скорости на путях витрины — прогнать `dev/bench` минимум на 100 000 товаров и обновить `docs/BENCHMARKS.md`.
- Пустые папки в манифесте компонента ломают установку (проверено: пустая `forms`).
- Данные бенчмарка лежат в таблицах `bn_*` той же базы; после замеров `php dev/bench/bench.php drop`.

# Выпуск версий и ленты обновлений

**Миграции БД обязательны.** Если у компонента изменился `sql/install*.sql`, он обязан получить новый файл в `sql/updates/mysql/<версия>.sql` (идемпотентный: `CREATE TABLE IF NOT EXISTS`, проверка колонки/индекса перед `ALTER`). `dev/release.py bump` проверяет это и отказывает, если файла нет (для осознанного пропуска — `--skip-migration-check`); `dev/release.py status --since …` печатает предупреждение. Манифест компонента должен содержать `<update><schemas><schemapath type="mysql">sql/updates/mysql</schemapath></schemas></update>`. Перед выпуском проверьте «обновление поверх предыдущей версии» на стенде.

Обновляется только пакет: `<updateservers>` есть **только** в `pkg_dharmashop.xml` и ведёт на коллекцию `updates/dharma-shop.xml` (её генерирует `dev/release.py feed`; адрес сохранён, потому что он зарегистрирован у уже установленных сайтов). В коллекции одна запись — пакет, со ссылкой на ленту `updates/pkg_dharmashop.xml`. У остальных расширений источника обновлений нет.

Версия у всех расширений и пакета одна — **версия выпуска** (`bump` ставит её везде). Ленты обновлений Joomla лежат в каталоге `updates/` этого репозитория (отдаются с `raw.githubusercontent.com`), архив пакета — в Releases этого же репозитория. Репозиторий `dharma-shop-updates` больше не используется.

```bash
./build.sh                                   # dist/pkg_dharmashop-<версия>.zip
DHARMA_SITE=/Volumes/Work/Server/www/test php dev/install.php "$PWD/dist/pkg_dharmashop-0.1.14.zip"
```

- C51: `script.php::upgradeFieldGroupTabs()` так же аддитивно добавляет `fieldgroups.tab_mode` со значением `fields`. Не деинсталлировать пакет; прежние группы и значения сохраняются. Административная папка `layouts` явно включена в манифест компонента.
- C59: `script.php::upgradeFieldValueStorage()` добавляет `field_values.num_end` и индекс, создаёт `category_field_values/category_field_texts`. Установка только обновлением; определения, опции, значения и пользовательские записи сохраняются. Автоматические сценарии без запроса пользователя не запускать.
- Изменения скорости на путях витрины — прогнать `dev/bench` минимум на 100 000 товаров и обновить `docs/BENCHMARKS.md`.
- Пустые папки в манифесте компонента ломают установку (проверено: пустая `forms`).
- Данные бенчмарка лежат в таблицах `bn_*` той же базы; после замеров `php dev/bench/bench.php drop`.

# Выпуск версий и ленты обновлений

**Миграции БД обязательны.** Если у компонента изменился `sql/install*.sql`, он обязан получить новый файл в `sql/updates/mysql/<версия>.sql` (идемпотентный: `CREATE TABLE IF NOT EXISTS`, проверка колонки/индекса перед `ALTER`). `dev/release.py bump` проверяет это и отказывает, если файла нет (для осознанного пропуска — `--skip-migration-check`); `dev/release.py status --since …` печатает предупреждение. Манифест компонента должен содержать `<update><schemas><schemapath type="mysql">sql/updates/mysql</schemapath></schemas></update>`. Перед выпуском проверьте «обновление поверх предыдущей версии» на стенде.

Все манифесты указывают на один источник — коллекцию `updates/dharma-shop.xml` (её генерирует `dev/release.py feed`); подробные ленты `updates/<расширение>.xml` лежат рядом и нужны только при установке.

Версия расширения — версия **выпуска, в котором оно менялось в последний раз**; у пакета версия выпуска всегда. Ленты обновлений Joomla лежат в `updates/` этого репозитория, архивы — в его Releases.

```bash
# 1. что изменилось с прошлого выпуска (справочно; тег основного репозитория)
python3 dev/release.py status --since v0.1.1
# 2. версия пакета и всех расширений := новая версия (<updateservers> остаётся только у пакета)
python3 dev/release.py bump 0.1.2 --since v0.1.1
# 3. миграции БД: любое изменение схемы — файл com_…/admin/sql/updates/mysql/<версия>.sql (идемпотентный) и <update><schemas> в манифесте компонента
# 4. коммит и push в main
# 5. выпуск: тег vВЕРСИЯ (версия в теге обязана совпасть с <version> в pkg_dharmashop.xml); дальше всё делает
#    .github/workflows/release.yml: собирает пакет, создаёт релиз (pkg_dharmashop-<версия>.zip, .sha256 и pkg_dharmashop.zip
#    для постоянной ссылки releases/latest/download/pkg_dharmashop.zip), пишет текст релиза (dev/release-notes.py: блоки
#    «Новая установка» и «Обновление», список изменившихся расширений, раздел из CHANGELOG.md) и коммитит ленты в updates/
git tag v0.1.2 && git push origin v0.1.2
# сухой прогон без публикации: Actions → «Выпуск версии» → Run workflow (результат — артефакт dry-run)
```

Проверка перед публикацией (стенд `dharmashoptest`): поставить прошлый пакет, выложить новые ленты на локальный сервер (`php -S 127.0.0.1:8099 -t <папка>` и сменить `location` в `#__update_sites`), убедиться, что Joomla находит только изменившиеся расширения, обновляется нужный плагин и пакет, а испорченная контрольная сумма блокирует установку.

Замечание про локальную проверку: PHP Kettle собран с библиотекой c-ares и при включённом VPN-туннеле без DNS в настройках сети не находит адреса («Could not resolve host»). Обновления на таком стенде проверяйте PHP ServBay (`/Applications/ServBay/package/php/8.4/current/bin/php cli/joomla.php update:extensions:check`) или добавьте DNS-серверы в настройках сети. Сервер раздачи для проверки — только по `http`: локальный HTTPS-сертификат PHP не принимает.
